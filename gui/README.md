# Локальный интерфейс курсовой работы

Этапы 1–4 завершены: запуск, воспроизведение, создание/сохранение сценариев и приёмочные проверки. Исходная версия симулятора — коммит 38f1b201; GUI находится в отдельном CMake-проекте и не меняет расчётные алгоритмы. [Аудит этапа 1](../docs/gui_stage_1_audit.md), [этапа 2](../docs/gui_stage_2_audit.md), [этапа 3](../docs/gui_stage_3_audit.md), [этапа 4](../docs/gui_stage_4_audit.md). [Итоговая инструкция и данные для глав 3–4](../docs/gui_handoff.md).

## Сборка и запуск на macOS

Нужны C++20, CMake ≥3.22, Ninja, Qt 6 ≥6.2 с Widgets/Concurrent/Test; для тестов симулятора — Python ≥3.9. Проверено с Qt 6.12.0, Apple Clang 17, macOS arm64. Если Qt отсутствует: `brew install qtbase`. Полный Qt SDK не нужен. Все команды из корня репозитория:

```sh
cmake -G Ninja -S gui -B build/kr-gui-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON -DCMAKE_PREFIX_PATH=/opt/homebrew/opt/qtbase
cmake --build build/kr-gui-release --parallel 4
./build/kr-gui-release/telemetry_gui --scenario examples/crash/scenario.json
```

При другом расположении Qt укажите свой CMAKE_PREFIX_PATH. Для офлайн JSON 3.12.0 добавьте к configure `-DFETCHCONTENT_SOURCE_DIR_NLOHMANN_JSON="$PWD/build/debug/_deps/nlohmann_json-src"`, если проверенная зависимость уже загружена туда. Бинарники GUI и telemetry_sim находятся рядом в build/kr-gui-release/. Можно собрать только приложение с его backend через `cmake --build build/kr-gui-release --target telemetry_gui --parallel 4`.

Из окна откройте JSON кнопкой «Открыть JSON…». Относительная delivery_trace разрешается от каталога JSON; CSV вручную выбирать не нужно. Выберите «Фиксированный» и «Round Robin — по кругу», нажмите «Запустить расчёт». В штатном crash ожидаются 4 завершённые/0 незавершённых задач, среднее обнаружение 17 мкс и восстановление 25 мкс. Ожидание процесса, хеширование входов и чтение журнала выполняются в фоне; индикатор показывает этап, а не выдуманный процент готовности.

Иной симулятор или каталог результата можно выбрать в окне либо аргументами `--simulator FILE`, `--results-root DIR`. По умолчанию используется соседний telemetry_sim, затем поиск в PATH; результаты пишутся в results/gui-runs относительно каталога запуска приложения. `--scenario FILE` только открывает вход, расчёт запускается кнопкой. Команды CLI: [контракт](../docs/cli.md).

## Результаты и ошибки

Каждая попытка получает новый каталог run-<UTC-время>-<UUID>. Внутри request.json фиксирует пути, SHA-256 и режимы; process.log содержит списки аргументов и диагностику; result/ появляется после успешной публикации native run. В нём обычные manifest.json, input/*, events.jsonl, metrics.json и CSV. Никакой --overwrite не передаётся. Ошибка validate не запускает run; её причина отображается в окне. Исправьте исходные файлы внешним редактором и нажмите запуск повторно.

После validate повторно проверяется неизменность обоих входов. Перед отображением проверяются код завершения, complete/вариант/горизонт manifest, SHA-256 снимков, порядок record_no/time_ticks, последний run_completed на горизонте, FNV-1a-64 журнала, наличие CSV и формат/баланс метрик. Расчёт с незавершёнными задачами может быть успешен. null не заменяется нулём: выводится reason с пояснением.

История результатов в текущем сеансе окна привязана к конкретным входам, режимам и каталогу. Смена сценария и ошибки не меняют прежние итоги; предыдущий успешный прогон можно выбрать в списке. При перезапуске GUI история пока не перечитывается автоматически, но все файлы остаются на диске. Новый сценарий и копия со своим списком отказов доступны кнопками в настройке запуска.

## Проверки

```sh
ctest --test-dir build/kr-gui-release --output-on-failure
ctest --test-dir build/kr-gui-release -R '^gui_stage1$' --output-on-failure
```

Дополнительные статистические тесты симулятора включаются через `-DTELEMETRY_ENABLE_STATISTICS_TESTS=ON -DPython3_EXECUTABLE="$PWD/build/statistics-venv/bin/python"` после установки tools/requirements-statistics.txt. GUI-тесты используют Qt Test и реальный backend; отдельный подставной процесс только копирует реальный контрольный результат и вносит повреждения протокола. Второй симулятор не реализован. В CTest GUI выполняется с offscreen; для живого окна macOS:

```sh
QT_QPA_PLATFORM=cocoa ./build/kr-gui-release/telemetry_gui_tests ./build/kr-gui-release/telemetry_sim ./build/kr-gui-release/telemetry_gui_fake_sim . results/kr-gui-stage1/live-checks
```

Каждый тестовый сеанс получает check-UUID, не перезаписывает предыдущие данные и сохраняет снимки окна/контрольные реальные прогоны. Для автоматизации выбора файла тест использует Qt-диалог вместо системного; само приложение по умолчанию открывает стандартный диалог платформы. Нажатия в живом окне проверяются Qt Test, ручная проверка человеком не заявляется.

Консольная сборка из корня работает прежним способом без Qt:

```sh
cmake -G Ninja -S . -B build/kr-cli-only -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build/kr-cli-only --parallel 4
./build/kr-cli-only/telemetry_sim validate --scenario examples/crash/scenario.json
```

## Воспроизведение журнала, этап 2

После расчёта выберите прогон в истории. Справа показан его источник и пара режимов. Воспроизведение начинается кнопкой «Воспроизвести»; «Пауза» сохраняет текущую позицию между событиями, «Шаг» ставит просмотр на паузу и применяет ровно одну следующую запись. Кнопка «Сначала» сбрасывает только просмотр. При ×1 полный горизонт занимает 8 секунд; ×8 соответствует примерно одной секунде. Точность ожидания ограничена планировщиком ОС и таймером Qt. Смена скорости сохраняет текущую позицию, меняя оставшееся ожидание.

Время на экране читается из time_ticks последней применённой записи. При равных отметках сохраняется исходный record_no, никакая сортировка по времени заново не выполняется. Служебные run_started/run_completed также занимают по одному шагу. Пока следующая запись ещё не применена, модельное время на экране остаётся прежним.

В таблице узлов «Работоспособен/Отказал» обновляется по crash, а ALIVE/SUSPECT/FAILED — только по heartbeat_observed/timeout_observed.after. Физически исправный узел может получить FAILED. В списке задачи выбирается ID; история показывает время, номер записи, попытку, исполнителя, отзыв с возвратом, новое назначение и принятие/отклонение результата. Поздний результат отозванной попытки остаётся строкой именно той попытки. Дополнительные физические записи показаны для объяснения начала/прерывания/окончания исполнения.

Нижние показатели и таблица Detection/Recovery по узлам читаются из metrics.json и всегда относятся ко всему прогону. Поэтому на промежуточной отметке 20 мкс в crash итог уже содержит 4 завершённые задачи. При null показывается reason с пояснением. Открытие другого входа не меняет старый выбранный результат; после успешного нового расчёта появляется отдельная запись истории. При выборе другого сохранённого прогона просмотр сбрасывается.

Формат журнала и таблица 2 записки сверены с реальными payload: reconfiguration.revoked[].task_id/node_id/attempt_no; task_assigned.assignment.task.id/node_id/attempt_no; result.attempt и decision. Значения enum в журнале нижнего регистра, для таблицы состояния они переводятся в верхний. Никаких новых порогов, детектора, планировщика или расчёта метрик внутри GUI нет. JSON для воспроизведения разбирается библиотекой nlohmann/json с целыми ID uint64 и временем int64; исходные файлы не переписываются.

```sh
ctest --test-dir build/kr-gui-release -R '^gui_stage[12]$' --output-on-failure
QT_QPA_PLATFORM=cocoa ./build/kr-gui-release/telemetry_replay_tests ./build/kr-gui-release/telemetry_sim . results/kr-gui-stage2/live-checks
```

Контроль: crash fixed/RR — физический crash 3 мкс, SUSPECT 10, FAILED 20, задачи 1/3 получают попытку 2 на узле 2, последний принятый результат возвращённого набора 28 мкс. Detection=17 мкс, Recovery=25 мкс, завершено 4/незавершено 0. Вспомогательно проверены короткий/длинный blackout, ложный FAILED и отказы всех узлов. Данные/снимки живого окна — results/kr-gui-stage2/live-checks/check-UUID/; timing.json содержит измеренную длительность ×1. Сами тесты нажимают кнопки Qt Test; ручная проверка человеком не заявляется.

Открытый журнал хранится в памяти для повторного воспроизведения, расход памяти растёт с числом записей. Загрузка/проверка выполняются в фоне. История сеанса пока не импортируется с диска после перезапуска приложения; сохранённые исходники/журналы остаются в каталогах прогонов. Автоматически созданные данные GUI игнорируются Git отдельно от прежних результатов НИР.

Использованные контракты Qt: [QProcess с отдельным списком аргументов](https://doc.qt.io/qt-6/qprocess.html). Сборка Qt остаётся отдельной от корневого проекта симулятора.

## Создание и копирование сценариев, этап 3

Выберите режимы в основном окне и нажмите «Новый сценарий…». На четырёх вкладках задаются узлы/производительность и отказы; горизонт/поток задач/seed; heartbeat/задержки/потери/перерывы; параметры детекторов. Все времена — целые микросекунды, производительность — единицы работы в секунду, трудоёмкость — единицы работы. Seed и ID поддерживают uint64 без преобразования через double. Для измерения throughput форма задаёт одно окно на весь горизонт.

«Создать и запустить» сохраняет generator_config.json, вызывает native generate и после complete генератора передаёт полученные JSON/CSV в прежний validate → run. Постоянный каталог generation-<UTC>-<UUID>/generated/ содержит сценарий, трассу, конфигурацию и generation_manifest.json. После расчёта этот JSON выбран в окне; его можно открыть снова обычной кнопкой. При ошибке параметры формы сохраняются до следующего открытия. Графический интерфейс не генерирует случайные работы или трассы самостоятельно.

Для готового JSON нажмите «Отказы / копия…», измените строки «ID узла — момент отказа» и сохраните под новым именем. Пустой список допустим. У каждого узла максимум один отказ, время от 0 до горизонта включительно; разные узлы могут отказать одновременно. Копия сохраняет исходные задачи и остальные параметры; правятся только значения crashes и delivery_trace. Байты вне этих двух значений остаются прежними, включая длинные числовые записи. CSV копируется побитово под уникальным именем delivery-UUID.csv в каталог выбранного JSON.

Перед публикацией копии выполняется native validate для временной пары. Проверяются неизменность исходного JSON/CSV и подготовленных файлов. Существующий целевой JSON, включая исходный сценарий и символьную ссылку, не заменяется. После успешной проверки публикуется новая пара; в окне выбирается её JSON. Запустить её можно обычной кнопкой расчёта. Старый выбранный результат и его снимки сохраняются. Сохранение не изменяет уже рассчитанный прогон и не имитирует отключение узла во время расчёта.

Каталоги copy-<UTC>-<UUID> содержат process.log проверки; временная пара очищается после окончания операции. При сбое/отключении питания между публикацией CSV и JSON может остаться отдельный CSV; общей транзакции двух файлов не заявляется. Исходная пара не перезаписывается. Стандартные правила полного формата/численных ограничений проверяет симулятор; форма выполняет предварительные проверки обязательных полей, диапазонов и ссылок.

```sh
ctest --test-dir build/kr-gui-release -R '^gui_stage[123]$' --output-on-failure
QT_QPA_PLATFORM=cocoa ./build/kr-gui-release/telemetry_editor_tests ./build/kr-gui-release/telemetry_sim ./build/kr-gui-release/telemetry_gui_fake_sim . results/kr-gui-stage3/live-checks
```

Данные и снимки тестового сеанса находятся в новом check-UUID. Для сохранения результатов пользователя сохраняйте весь каталог generation/прогона либо выбранную пару JSON/CSV. Результаты текущего сеанса в памяти окна не импортируются автоматически при перезапуске; готовые сценарии открываются с диска.

## Итоговая проверка, этап 4

При BUILD_TESTING=ON зарегистрированы 99 CTest: 95 прежних и 4 группы GUI. При TELEMETRY_ENABLE_STATISTICS_TESTS=ON добавляется прежняя статистическая группа — всего 100. Одна группа GUI содержит несколько Qt Test проверок: 26/7/13/26 соответственно, включая setup/cleanup. Последняя проверяет 6 условий × 4 сочетания режимов, а не превосходство одного алгоритма.

```sh
ctest --test-dir build/kr-gui-release --output-on-failure
ctest --test-dir build/kr-gui-release -R '^gui_stage[1234]$' --output-on-failure
QT_QPA_PLATFORM=cocoa ./build/kr-gui-release/telemetry_acceptance_tests ./build/kr-gui-release/telemetry_sim . results/kr-gui-stage4/acceptance
```

Матрица использует baseline, crash, blackout, long_blackout, no_alive и копию crash с неизвестным узлом. Для каждого сочетания проверяются реальные процессы и результаты, сохранность входов и показания окна. В check-UUID/acceptance.json — конфигурация, SHA-256, ожидаемое/фактическое поведение, метрики и переходы; acceptance.csv — компактная таблица; подкаталоги содержат входные снимки, журналы и process.log. Для каждого из шести условий сохранён снимок окна fixed/RR. Сводка окончательной проверки — results/kr-gui-stage4/final_checks.json. Подробности фактически выполненных команд и ограничений — в аудите этапа 4.

Для AddressSanitizer/UndefinedBehaviorSanitizer на проверенной машине используется отдельная Debug-сборка LLVM:

```sh
cmake -G Ninja -S gui -B build/kr-gui-sanitize -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON -DCMAKE_PREFIX_PATH=/opt/homebrew/opt/qtbase -DCMAKE_CXX_COMPILER=/opt/homebrew/opt/llvm/bin/clang++ -DTELEMETRY_ENABLE_ASAN=ON -DTELEMETRY_ENABLE_UBSAN=ON
cmake --build build/kr-gui-sanitize --parallel 4
ASAN_OPTIONS=detect_leaks=0 UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 ctest --test-dir build/kr-gui-sanitize -R '^gui_stage[1234]$' --output-on-failure
```

Это проверка доступа к памяти и UB в собственном коде; утечки здесь отключены, системные библиотеки и установленный Qt не пересобраны с санитайзерами. Переносимость на Windows/Linux и упаковка .app не проверялись. Для работы требуется установленный Qt; выдаваемый исполняемый файл запускается из терминала.
