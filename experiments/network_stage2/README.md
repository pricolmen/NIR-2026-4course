# Этап 2 Исследование jitter и потерь heartbeat

Цель — проверить существующие fixed/adaptive в условиях меняющейся доставки сообщений. Используются обёртка [этапа 1](../../docs/seed_series.md), существующие generate/batch и исходные метрики C++. Новых формул, постоянного запаса alpha, минимального стандартного отклонения или новых распределителей здесь нет.

## Зафиксированный план

[plan.json](plan.json) задаёт явные seed 2001–2010 (в файле перечислены все десять значений), сетевые уровни и два режима. [base_generator.json](base_generator.json) содержит остальные настройки. Эти файлы не подбирались по полученным результатам.

| Параметр | Значение |
|---|---|
| Узлы | 2, одинаковые p=1000000 ед. работы/с |
| Задачи | 40; работа uniform_real в [8000;12000] |
| Поступления | 0, 10, …, 390 мс; один фиксированный уровень интенсивности |
| Горизонт и окно throughput | 600 мс; (0;600] мс |
| Heartbeat | H=10 мс |
| Fixed / начальные пороги | tau0=20 мс; kappa=2 |
| Adaptive | M=3, min_intervals=2, c=2 |
| Среднее заданной задержки | 10 мс во всех ячейках |
| Полуразмах jitter J | 0, 5, 10 мс |
| Вероятность потери q | 0, 0.05, 0.15 |
| Режим healthy | Настоящих отказов нет |
| Режим crash | Один crash узла 1 в 200 мс |
| Blackout | Не задаётся |

Горизонт даёт 60 потенциальных heartbeat каждого узла и участок наблюдения до и после crash. Он длиннее интервала поступления задач и включает дренирование очередей. Этот масштаб увеличен относительно технической пробы этапа 1; дополнительные уровни нагрузки здесь не исследуются.

Получается 3×3×2=18 ячеек, по 10 сохранённых реализаций и 4 сочетания в каждой: **180 наборов входов, 720 моделирований**. Между ячейками одинаковые seed используются для сопоставления одного потока задач; эти связанные ячейки не считаются дополнительными независимыми повторами одной настройки.

Jitter здесь — симметричный разброс неотрицательной задержки относительно фиксированного среднего:

| J | Равномерная целая задержка |
|---|---|
| 0 мс | [10;10] мс — постоянная задержка, не нулевая |
| 5 мс | [5;15] мс |
| 10 мс | [0;20] мс |

Входные числа выражены целыми микросекундными тиками. Интервалы распределения включают обе границы. Математическое среднее каждого распределения равно 10 мс; выборочное среднее конечного CSV может отличаться. При J=10 мс возможна перестановка heartbeat. Больший jitter не обязан монотонно ухудшать каждый показатель адаптивного детектора: он сам меняет пороги по истории интервалов.

Потери — существующее независимое решение u<q для каждого потенциального сообщения генератора, а не burst/коррелированная модель сети. Трассы включают потенциальные отправки после crash и приёмы за горизонтом; число записанных lost не равно числу фактически потерянных исполненных отправок. Период поступления и число узлов не варьируются: исследования интенсивности/четырёх узлов относятся к этапу 7.

## Запуск

Из корня проекта:

```sh
cmake -G Ninja -S . -B build/experiment-stage2-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build/experiment-stage2-release --parallel 4
ctest --test-dir build/experiment-stage2-release --output-on-failure
python3 tools/run_network_series.py --plan experiments/network_stage2/plan.json --program ./build/experiment-stage2-release/telemetry_sim --out results/experiment-stage2-network
```

Для сборки без сети к первой команде добавьте `-DFETCHCONTENT_SOURCE_DIR_NLOHMANN_JSON="$PWD/build/debug/_deps/nlohmann_json-src"`, если зависимость сохранена в этом каталоге. Другую собранную программу можно передать через --program. Только стандартная библиотека Python; сеть, сторонние Python-пакеты и контейнеры для серии не нужны.

--out обязан быть новым; существующие каталоги, в том числе пустые и symlink, отклоняются. Для нового повторения всей генерации укажите другое имя, например results/experiment-stage2-regenerated. Это не добавляет независимых реализаций: используются прежние seed.

## Сохранённые материалы

| Путь внутри results/experiment-stage2-network | Содержание |
|---|---|
| plan.json, base_generator.json | Точные копии исходных настроек |
| templates/*.json | 18 конкретных конфигураций; явно меняются только delivery и crashes |
| cases/<id>/ | Полная серия этапа 1 с конфигурациями каждого seed, входами, метаданными и batch |
| cases/<id>/batch/runs/000001/... | Четыре варианта сохранённого входа; seed сопоставляется через series_manifest.json |
| network_comparison.csv | Строки исходного native comparison.csv всех ячеек с пометками условий |
| network_summary.csv | Строки исходного native summary.csv с пометками условий; средние заново не рассчитываются |
| network_manifest.json | Статус, план/хеши, команды и проверки входов/результатов |
| logs/ | stdout/stderr каждого вызова обёртки этапа 1 |

ID healthy_j5000_q1 означает: без crash, J=5000 тиков=5 мс, q1 — второй элемент loss_probabilities, то есть 0.05. q0=0, q2=0.15. Точные значения всегда записаны в manifest и CSV. Для crash меняется только расписание реального отказа.

## Что проверяется

- В каждом seed во всех 18 ячейках точно совпадают задачи, узлы, параметры детекторов, горизонт и окна. Отличается только сценарий crash и материализованная доставка.
- Для одного jitter/q/seed полная delivery.csv побитово совпадает в healthy и crash: различие результата не вызвано новой случайной трассой.
- При изменении только q и фиксированных jitter/seed задержки совпадают, а маски потерь вложены. Это проверяется по фактическим CSV.
- Между разными J не обещается совпадение конкретных масок потерь: диапазон uniform_int может менять потребление RNG. В этих сравнениях фиксируется номинальная вероятность q, а полные трассы сохраняются.
- Четыре сочетания получают одинаковые байты scenario.json/delivery.csv. Проверяются complete, баланс/инварианты и хеши содержательных результатов.
- Для одного детектора состояние/классификация узлов совпадает между RR и LL. Различия возврата задач и Recovery при этом допустимы.
- Число настоящих crash равно сумме корректно обнаруженных, FN и crash после прежнего ложного исключения. Отсутствующий Detection не превращается в ноль.

Для воспроизводимости на сохранённых входах можно повторить отдельную ячейку без generate:

```sh
python3 tools/run_seed_series.py --reuse-series results/experiment-stage2-network/cases/crash_j10000_q2 --program ./build/experiment-stage2-release/telemetry_sim --out results/experiment-stage2-replay-crash-j10000-q2
```

Скрипт этапа 1 сверяет содержательные результаты на том же бинарнике и сохраняет отдельный manifest; такие повторы не включаются в научную выборку серии.

## Чтение результатов и границы

Сначала учитывайте завершённость, FP/FN, crash после ложного исключения и число определённых Detection/Recovery, затем условные средние. Если узел был ложно исключён до своего crash, это FP и отдельный late-crash, а не корректное обнаружение с нулевой задержкой. Поэтому FN=0 не означает, что все десять crash дали определённый Detection.

FP считаются за весь горизонт 600 мс, в том числе после завершения задач; не каждый FP приводит к незавершённости. В healthy для каждой настройки наблюдаются 20 узлов в 10 реализациях. Число незавершённых задач в summary — сумма по 10 запускам, то есть из 400 поступивших задач на вариант. В crash один настоящий отказ на реализацию: максимум 10 определённых Detection. Средние Recovery/latency могут рассчитываться по разным выборкам — их размеры нужно сохранять рядом со средними.

Основное окно throughput включает весь опыт и период дренирования после последнего поступления. Его значение не следует отождествлять с производительностью узла или интенсивностью источника. Для среднего P95 summary сначала берётся P95 каждого запуска; это не P95 объединённых 400 задач.

[Отчёт этапа 2](../../docs/experiment_stage_2_audit.md) содержит фактические проверки и описательные наблюдения. Доверительные интервалы, графики и обобщённая статистическая обработка относятся к этапу 8. Настройки tau0/kappa/c/M в этой серии фиксированы; новые формулы не вводятся. Исследование отдельных граничных времён и sigma=0 остаётся этапом 9.
