# Этап 5 Коэффициент c адаптивного детектора

Коэффициент c задаёт запас перед выборочным стандартным отклонением интервалов приёма heartbeat. После прогрева действует прежняя формула raw_S=max(H,μ+cσ), raw_F=κ×raw_S. Здесь H — период heartbeat, μ — средний интервал между допустимыми приёмами, σ — выборочное стандартное отклонение с делителем m−1 для m интервалов. Пороги округляются до целых тиков: S=ceil(raw_S), F=max(S+1,ceil(raw_F)). S — интервал до SUSPECT, F — до окончательного FAILED; оба отсчитываются от последнего принятого сообщения.

До накопления min_intervals действует начальный raw_S=T₀, независимо от c. При c=0 после прогрева сохраняется max(H,μ); это допустимый режим существующей формулы. c не меняет пороги fixed. Более высокий c увеличивает запас при одной и той же истории с σ>0, однако разные c могут вызвать разные ранние FAILED и последующие истории приёма. Монотонность всех итоговых метрик не предполагается.

Существующий C++ CLI выполняет моделирование, округление и расчёт метрик. [run_coefficient_series.py](../../tools/run_coefficient_series.py) вызывает [обёртку этапа 1](../../docs/seed_series.md) только через --reuse-series и --detector-overrides с патчем `{"adaptive":{"c":VALUE}}`. Новая реализация метрик, alpha и минимальное sigma не добавляются.

## План и неизменные условия

[plan.json](plan.json) задаёт **c=0,0.5,1,2,3,4**, seed 2001–2010 и шесть сохранённых источников этапа 2. c должен быть конечным числом >=0. Исходное c=2 включено как контроль совпадения с этапом 2; fixed_rr/fixed_ll служат неизменным контролем на каждом уровне c.

| Профиль | Источники без отказа / с отказом | Задержка | Вероятность потери q |
|---|---|---|---:|
| Чистый | healthy_j0_q0 / crash_j0_q0 | 10 мс | 0 |
| Средний | healthy_j5000_q1 / crash_j5000_q1 | [5;15] мс | 0.05 |
| Напряжённый | healthy_j10000_q2 / crash_j10000_q2 | [0;20] мс | 0.15 |

Выбраны чистый, средний и крайний профили исходной сетки до просмотра результатов новой серии. Между профилями меняются и jitter, и q: межпрофильное сравнение не изолирует один сетевой фактор. Эффект c исследуется внутри каждого сохранённого профиля.

Не меняются: два узла по 1000000 ед. работы/с, 40 задач работы 8000..12000; поступления каждые 10 мс от 0 до 390 мс; горизонт 600 мс и окно throughput (0;600] мс; H=10 мс, T₀=20 мс, κ=2, M=3, min_intervals=2. M — максимальное число интервалов в истории, min_intervals — минимум для прогрева. В crash узел 1 отказывает в 200 мс, blackout отсутствует. Задачи и delivery.csv повторно не генерируются. Входы берутся непосредственно из этапа 2, с исходными T₀ и κ, а не из изменённых ячеек этапов 3–4.

6 источников × 6 c × 10 seed × 4 сочетания = **1440 моделирований**: 720 adaptive и 720 контрольных fixed. Это 60 исходных наборов на шести уровнях, а не 360 независимых реализаций. На профиль остаются десять seed; повторы и параметры не увеличивают независимую выборку.

## Сборка и запуск из корня проекта

```sh
cmake -G Ninja -S . -B build/experiment-stage5-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build/experiment-stage5-release --parallel 4
ctest --test-dir build/experiment-stage5-release --output-on-failure
python3 tools/run_coefficient_series.py --plan experiments/coefficient_stage5/plan.json --source-network results/experiment-stage2-network --program ./build/experiment-stage5-release/telemetry_sim --out results/experiment-stage5-coefficient
```

Для автономной настройки добавьте `-DFETCHCONTENT_SOURCE_DIR_NLOHMANN_JSON="$PWD/build/debug/_deps/nlohmann_json-src"`, если сохранённая зависимость доступна там. Бинарник можно заменить через --program. --source-network должен содержать завершённые исходные серии с входами, manifests и происхождением генерации; отсутствующие материалы не регенерируются скрыто.

--out обязан быть новым, даже если существующий каталог пуст. При повторном исполнении выбирайте другое имя. Выход внутри исходной сетевой серии запрещён. Различия параметров задаются только явно в плане.

| Путь в результате | Содержание |
|---|---|
| plan.json, source_network_manifest.json | Снимки плана и происхождения источника |
| overrides/coefficient_*.json | Патчи только adaptive.c |
| cases/<source_case>_c<value>/ | Полные входы, provenance, четыре варианта, native batch |
| coefficient_manifest.json | Seed, параметры, команды/коды выхода, хеши, проверки |
| coefficient_comparison.csv | Исходные строки native comparison с подписями профиля и c |
| coefficient_summary.csv | Исходные строки native summary с той же разметкой |
| logs/ | stdout/stderr вызовов обёртки |

Точка в имени заменяется на p: c0p5 означает c=0.5. Числа читаются/сохраняются через Decimal без сужения до Python float. Native scenario_id/repeat_id сохраняются от источника, поэтому при группировке объединённого CSV учитывайте также c или case_id. Исходные сведения генерации остаются provenance, а не выдаются за описание новой генерации.

Повтор готовой ячейки:

```sh
python3 tools/run_seed_series.py --reuse-series results/experiment-stage5-coefficient/cases/crash_j10000_q2_c3 --program ./build/experiment-stage5-release/telemetry_sim --out results/experiment-stage5-replay-crash-c3
```

## Контроль и интерпретация

Драйвер требует, чтобы сценарий отличался от источника только adaptive.c: window/min_intervals, все остальные поля, задачи и параметры среды сохраняются. delivery.csv совпадает побитово, четыре варианта получают одинаковые входы. Проверяются complete, баланс задач, классификация crash, хеши пяти содержательных файлов и равенство оценки одного детектора при RR/LL.

При c=2 должны совпасть все 240 вариантов с этапом 2. Кроме того, все 720 fixed-вариантов на любых c должны совпасть с соответствующими fixed источника по events.jsonl, metrics.json, tasks.csv, attempts.csv, nodes.csv. Эти контроли частично пересекаются: 120 исходных fixed-вариантов входят в обе группы; их нельзя суммировать как разные запуски. В фактической серии дополнительно проверяется неизменность adaptive между c при чистой связи.

Служебные manifests могут различаться путями/происхождением. Повреждённые входы, несовместимый контроль, конфликт выхода, изменение программы/скриптов и ненулевой код CLI не считаются успехом. Сохраняются failed и логи. Native CLI отвечает за численную представимость порогов. Для контрольного совпадения нужна совместимая программная среда; переносимость между платформами не заявляется. Конечный контроль не доказывает эквивалентность произвольных программ, поэтому в фактическом этапе дополнительно проверены исходники C++, сборка и её команда. Хеш программы, build-info, снимки исходников и доступный Git записываются в дочерних manifests.

FP — ложное исключение узла; FN — необнаруженный физический отказ по текущей классификации; Late — crash после предшествующего ложного исключения. Ndet — число корректных определённых Detection (задержек обнаружения). При FN=0 и Late>0 не все crash обнаружены корректно. Отсутствующее значение не заменяется нулём.

Recovery — время завершения возвращённой работы; Nrec — число определённых наблюдений, а не всего потока задач. Учитывайте незавершённость и размеры выборок рядом со средними. Healthy содержит 20 узлов и 400 задач на настройку в десяти реализациях, crash — десять физических отказов. Низкая задержка завершённой части при потере оставшейся работы не означает хорошего результата.

CSV сохраняют native средние показателей отдельных запусков: это не среднее объединённых задач и не объединённый P95. Доверительные интервалы/графики относятся к этапу 8. Отдельный анализ граничных времён и σ=0 остаётся этапом 9; чистый профиль здесь служит контролем. Универсальный оптимальный c и преимущество одного алгоритма не устанавливаются. Фактические результаты и самопроверка: [аудит этапа 5](../../docs/experiment_stage_5_audit.md).
