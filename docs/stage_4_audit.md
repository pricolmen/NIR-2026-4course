# Этап 4: RR, LL, нагрузка и самоаудит

Дата: 19 октября 2026, Europe/Moscow. Этап 5 не начат.

## Реализация

Добавлены [RoundRobin, LeastLoaded и LoadLedger](../include/telemetry/core/scheduling.hpp), их [реализация](../src/core/scheduling.cpp), [Dispatcher](../include/telemetry/core/dispatcher.hpp) и [связывание с TaskStore](../src/core/dispatcher.cpp). `NodeDefinition` содержит только ID и постоянную производительность. Входы — ручные задачи/результаты и итоговый ALIVE-набор; физические данные, движок, JSON и сеть в ядро не передаются.

RR хранит следующего исполнителя, выбирает/продвигается за O(1), перестраивает доступность отдельно, сохраняет ориентир через исключения и пустой список. LL линейно выбирает минимум W/p среди ALIVE и разрешает точное равенство меньшим ID. Полная работа выполняемой и ожидающей задач входит в W, время её не уменьшает. Каждое назначение обновляет счётчик до следующего выбора; принятие/отзыв снимают работу один раз, пустой узел получает точный ноль.

Dispatcher владеет реестром и счётчиками; наружу доступны константные представления. Предварительная проверка арифметики выполняется до мутации TaskStore, а внутренний обработчик события применяет нагрузку и курсор до внешнего callback. Классификация результата вынесена в один `TaskStore::inspect_result`, используемый также самим приёмом: двух расходящихся проверок допустимости нет. Старые/неверные результаты не обращаются к нагрузке указанного в них неизвестного узла.

Численное уточнение реализации — компенсированная сумма Neumaier на long double. Она сохраняет малую работу после снятия очень крупной. Формула W/p и правило LL не меняются. Hash-таблица служит только для адресации узла; канонический порядок определяется отдельным отсортированным вектором. Получение счётчика по готовой записи O(1), поиск записи по ID O(1) в среднем, LL O(A) в среднем; детали подготовки RR и независимого пересчёта приведены в [scheduling.md](scheduling.md).

## Содержательные проверки

| Группа | Проверенные последствия |
|---|---|
| `scheduling_rr` | Неупорядоченный исходный каталог, минимальный первый ID, обычный цикл, исчезновение предполагаемого следующего, возврат из SUSPECT без сброса, пустой список с сохранением ориентира, совместное исключение следующего и его преемника, совместный возврат, неверные/повторные ID |
| `scheduling_ll` | Нормализация по p, одинаковые/разные p, разрешение равенства по ID независимо от обхода, отличие соседних вещественных нагрузок без epsilon, фильтрация ALIVE, пустой набор, обновление после каждой команды одной отметки, отсутствие уменьшения работы от времени |
| `scheduling_integration` | RR `[1,2,1,2]` для работы `[4,2,4,2]`, учёт текущей и ожидающей полной работы, однократное снятие, повторный отзыв, старые результаты до/после переназначения, новая попытка с полной работой, точный итоговый ноль, ошибка наблюдателя после согласованного обновления, запрет изменения доступности из callback |
| `scheduling_availability` | Прекращение новых назначений недоступному узлу без отзыва старых, принятие его актуального результата, сохранение FIFO при пустом ALIVE, сохранение позиции после возврата, атомарное отклонение неверной доступности, монотонность времени с учётом её изменений |
| `scheduling_numeric` | `10^20 + 1 - 10^20` оставляет работу 1, точный ноль после последней задачи, неверные p/дубликаты каталога, underflow нагрузки и overflow суммы отклоняются до ошибочного изменения счётчика/назначения |
| 16 регрессионных тестов | Время/ID, TaskStore и журнал, JSON, CLI/метаданные с номером этапа 4 |

Наблюдатель в интеграционном тесте после каждого события независимо проверяет реестр и пересчитывает нагрузки по актуальным назначениям. Только этот пересчёт использует допуск из контракта; LL сравнивает нагрузки без epsilon. Проверяются также число назначений, принадлежность их узлов каталогу, конечность/положительность нагрузки и точный ноль пустой записи.

Дополнительно проверяются локальные Markdown-ссылки/форматирование, compile_commands.json (C++20, предупреждения, NDEBUG, обе опции санитайзеров, отсутствие JSON в core/его тестах), CMake-граница `core → common` и `git diff --check`. Общие типы и журнал предыдущих этапов сохранены; TaskStore получил только общий метод предварительной классификации результата.

Это самоаудит основного агента без субагента по принятому порядку до этапа 10. Независимый аудит и уровень High не заявляются. План и DOCX не изменялись; отчёты предыдущих этапов сохранены. Коммит и staging не выполнялись.

ALIVE-набор пока передаётся вручную целиком. Детекторы, автоматическое объединение изменений одной отметки, совместный отсортированный возврат назначений FAILED, физическая среда, файлы сценариев и метрики не реализованы. Каталог узлов во время запуска неизменяем. Ошибка арифметики или журнала означает ошибочный запуск: dispatch не является транзакцией всей пачки, прежние успешные назначения сохраняются целостными. Искусственное исчерпание памяти не тестировалось. Linux/GCC/Windows и другая точность long double не проверены. Тестовые примеры не являются результатами научного сравнения.
