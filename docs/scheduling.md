# Распределение и нагрузка

Этап 4. [Стратегии и LoadLedger](../include/telemetry/core/scheduling.hpp), [реализация стратегий](../src/core/scheduling.cpp), [Dispatcher](../include/telemetry/core/dispatcher.hpp), [связывающий код](../src/core/dispatcher.cpp). Правила — разделы 6.2–6.3 плана и [контракт](model_contract.md).

## Входы и границы

Dispatcher получает фиксированный каталог `NodeDefinition{id, performance}`, политику RR/LL и optional-наблюдатель. Производительность конечна, положительна и задана в единицах работы/с; ID уникальны. Все исходные узлы сначала доступны. В каталоге нет фактического состояния, crash, локальной физической очереди или остаточной работы. Пустой каталог поддержан.

`arrive`, `receive_result` и `revoke_assignment` используют реестр этапа 3. `set_alive(at, ids)` принимает один итоговый набор логически ALIVE для всех изменений отметки; неизвестные/повторные ID отклоняются, входной порядок нормализуется. Временно недоступный узел сохраняет старые назначения и нагрузку; его актуальный результат по-прежнему допустим. Отзыв всех назначений FAILED и группировка изменений будут реализованы на этапах 6 и 10. Метод не выводит состояние из физической среды.

`dispatch(at)` выдаёт FIFO до опустошения либо отсутствия ALIVE, возвращает последовательность команд и не ждёт свободного исполнителя. При пустом ALIVE задачи остаются в очереди. Реестр и таблица нагрузки снаружи доступны только для чтения. Изменяющие операции не допускают повторный вход из наблюдателя; время включает также изменения доступности и пустой dispatch и не убывает.

## Round Robin

`RoundRobin` — отдельный класс с исходными ID, подготовленным отсортированным списком ALIVE и позицией следующей выдачи. Первый выбор — минимальный исходный ID. `peek()` не изменяет позицию; после совершённого назначения `advance()` сохраняет следующего исполнителя по кругу. Пустой dispatch позицию не сдвигает.

При замене ALIVE сохраняется предполагаемый следующий ID. Если он отсутствует, берётся первый доступный ID после него в циклическом порядке. В пустом списке ориентир сохраняется до возвращения доступности. Возврат узла не сбрасывает позицию на минимальный ID. Одновременные изменения передаются одной заменой списка, без промежуточных корректировок.

Чтение выбора и продвижение O(1). Подготовка при изменениях отдельно сортирует список и проверяет принадлежность исходному каталогу: O(A log A + A log N). Dispatcher хранит итоговый ALIVE-набор, а RR — собственный подготовленный список/курсор; замена выполняется без внешнего callback между обновлениями. У LL отдельного изменяемого курсора нет.

## Least Loaded

`LeastLoaded::select(alive, loads)` — отдельная стратегия, линейно просматривающая только заданные ALIVE:

```text
W_i = сумма полной исходной работы актуальных неотозванных незавершённых назначений
Load_i = W_i / p_i
```

Выполняемая работа входит целиком наравне с ожидающей. Течение времени не уменьшает W. При одинаковой нагрузке выбирается меньший ID независимо от порядка входного списка. Сравнение использует `<` и точное `==`, без epsilon. Пустой список даёт `nullopt`. Каждая новая команда увеличивает нагрузку до выбора следующей задачи той же отметки.

Нагрузка вычисляется из сохранённых счётчиков за O(1), без сканирования задач. Адресация узла по ID через hash-таблицу — O(1) в среднем; выбор LL — O(A) в среднем. Канонический порядок узлов хранится отдельно в отсортированном векторе; порядок обхода hash-таблицы нигде не определяет решения или журнал.

## Численная реализация и целостность

Счётчик работы использует `long double` и компенсацию суммирования Neumaier. Это техническое уточнение вычисления суммы, не новое определение Load: компенсация сохраняет малую работу при последующем снятии очень крупной. Число актуальных назначений учитывается отдельно с проверкой переполнения. При снятии последнего назначения обе части суммы устанавливаются в точный ноль. Произвольного обнуления нагрузки при исключении из ALIVE нет.

Непредставимый/неконечный итог суммы или отношения W/p отклоняется; потеря положительной нагрузки до нуля является ошибкой, а не равенством нагрузок. Ledger — счётчик, не второй реестр попыток: прямой пользователь его `add/remove` обязан передавать исходную работу соответствующего назначения. В рабочем Dispatcher доступ к Ledger только константный, работу берёт сам Dispatcher из TaskStore.

До назначения/принятия/отзыва Dispatcher проверяет арифметику будущего изменения без мутации. TaskStore использует единый `inspect_result` для классификации; отвергнутые результаты до таблицы нагрузок не доходят. Внутренний наблюдатель выполняет то же уже проверенное арифметическое изменение, при необходимости сдвигает RR и затем передаёт событие внешнему наблюдателю. Между предварительной проверкой и применением нет внешних callback и изменений каталога. Внешний наблюдатель видит согласованные реестр и нагрузку.

Ошибка внешнего журнала остаётся фатальной для запуска; обновлённое логическое состояние не откатывается. Dispatch — последовательность отдельных назначений: если арифметика последующей команды недопустима, прежние команды уже совершены, но сам запуск ошибочен и не может участвовать в научном сравнении. Искусственное исчерпание памяти не тестировалось.

`Dispatcher::validate_invariants()` независимо пересчитывает нагрузку по актуальным назначениям, проверяет их исполнителей, число назначений и точный ноль пустого узла. Только при сравнении сумм используется согласованный допуск `64 * epsilon(long double) * max(1,n) * max(1,sum_abs_work)`. Допуск не исправляет значения и не участвует в выборе LL. Эта проверка O(N*T) предназначена для тестов/аудита, а не горячего пути выбора.

## Проверки

[scheduling_tests.cpp](../tests/scheduling_tests.cpp): пять групп RR, LL, интеграции с TaskStore, доступности и численных границ. Ручные последовательности показывают RR `[1,2,1,2]` и LL `[1,2,2,1]` для работы `[4,2,4,2]` при равных p; при p `[1,2]` LL выбирает `[1,2,2,2]`. Это ожидания тестов, не измерения эффективности алгоритмов.

Проверены исчезновение следующего узла, совместные исключения/возвраты, пустой ALIVE, отсутствие сброса позиции, влияние p, различие соседних вещественных нагрузок, полная работа без убывания от времени, однократное снятие, прежний результат после переназначения, `10^20 + 1 - 10^20 = 1` в счётчике и численные ошибки. Callback в тесте проверяет инварианты после каждого события; отдельно проверяются ошибка журнала и запрет повторного входа. Полные результаты — в [отчёте этапа 4](stage_4_audit.md).

На этапе 6 `set_alive` стал обёрткой над `apply_availability` без новых FAILED и выдаёт событие итоговой доступности. Совместный отзыв, окончательность FAILED и затраты подготовки Dispatcher описаны в [reconfiguration.md](reconfiguration.md). При новых FAILED обнуляется вся отозванная логическая нагрузка соответствующих узлов; исключение только в SUSPECT её сохраняет.
