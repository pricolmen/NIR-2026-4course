# Время, идентификаторы и численные правила

Действующие численные правила готового стенда. Основание — раздел 5 плана и [контракт модели](model_contract.md). Связанные модули: [детекторы](detectors.md), [движок](event_loop.md), [чтение сценариев](scenario_format.md). Общая архитектура и прослеживаемость: [architecture.md](architecture.md).

## Представление и API

[time.hpp](../include/telemetry/common/time.hpp) задаёт отдельные `telemetry::SimTime` и `SimDuration`. Внутри — `std::int64_t`, диапазон `[0, INT64_MAX]`. Конструкторы явные и принимают только целые значения; `bool` и вещественные типы запрещены на этапе компиляции. Отрицательный целый вход отклоняется до преобразования, слишком большой беззнаковый — до сужения. Создание по умолчанию даёт действительный ноль.

Единицы: `ticks_per_second = 1 000 000`, `tick_ns = 1000`, один тик равен микросекунде. `.ticks()` возвращает точное целое; даже 9007199254740993 и INT64_MAX не проходят через вещественное представление. Сценарные `_ticks` читаются напрямую как целые в загрузчике этапа 9. Поддержка JSON в этих типах отсутствует.

| Операция | Результат / условие |
|---|---|
| `SimTime + SimDuration` | Новая отметка; сумма проверяется до сложения |
| `SimTime - SimDuration` | Новая неотрицательная отметка |
| `SimTime - SimTime` | Неотрицательный прошедший интервал; обратный порядок отклоняется |
| `SimDuration +/- SimDuration` | Неотрицательный интервал с проверкой диапазона |
| Сравнение одинаковых типов | Точное целочисленное сравнение, без epsilon |
| `deadline_within(now, delay, horizon)` | `optional<SimTime>`: точный срок до горизонта включительно либо `nullopt` строго за горизонтом |
| `seconds(duration)` | `long double` только для отображения и метрик, не для очереди событий |

Отметки нельзя складывать между собой, а длительность нельзя неявно превратить в отметку. Для отсутствующего момента используется `std::optional<SimTime>`: пустое значение отличается от присутствующей отметки 0. `deadline_within` сначала проверяет `now <= horizon`, затем сравнивает `delay` с `horizon - now`, и лишь потом складывает. Поэтому даже запрос `now = INT64_MAX - 1, delay = INT64_MAX` безопасно возвращает отсутствие срока за горизонтом. Нулевой горизонт допустим для этого арифметического помощника; положительность горизонта сценария проверяется загрузчиком на этапе 9. Фазовые ограничения реализованы на этапе 7 в EventLoop: нулевая задержка допускает только последующую фазу текущей отметки.

## Вычисляемые длительности

Реализация — [time.cpp](../src/common/time.cpp). Все промежуточные вычисления используют `long double`. `ceil_ticks(raw)` принимает конечное неотрицательное значение в тиках, применяет `ceil`, проверяет диапазон и только затем преобразует результат в `int64_t`.

Проверка верхней границы использует точную исключённую границу `2^63`, полученную `std::ldexp(1.0L, 63)`: округлённый результат должен быть строго меньше неё. Нельзя проверять `raw <= static_cast<long double>(INT64_MAX)`, поскольку на платформах с 53 битами мантиссы, включая текущую Apple arm64, этот cast уже округляет максимум вверх до `2^63`. На платформах с более точным `long double` корректно принимается и точно представимый INT64_MAX. Вещественное вычисление не обещает различать отдельные тики на всём диапазоне int64; точные внешние времена остаются целыми.

Обработка:

```text
processing_duration(w, p) = max(1, ceil((w / p) * ticks_per_second))
```

Работа и производительность конечны и строго положительны; `p` — работа/с. Проверяется конечность и положительность результата деления и масштабирования. Потеря положительной величины до нуля из-за underflow отклоняется явно. Представимая положительная обработка короче тика занимает один тик. Бесконечный промежуточный результат и конечная длительность вне int64 отклоняются, а не заменяются насыщением.

Преобразование порогов:

```text
suspect = ceil(raw_suspect)
failed  = max(suspect + 1, ceil(raw_failed))
```

`round_thresholds` принимает уже вычисленные математические пороги, проверяет конечность, положительность первого и порядок `raw_failed >= raw_suspect`; возвращает исходные значения и оба представимых интервала в `RoundedThresholds`. Совпадение представленных вещественных исходных порогов допускается: обязательный дополнительный тик сохраняет отдельную стадию SUSPECT. Формулы fixed/adaptive и проверка `kappa > 1` реализованы в [детекторах](detectors.md). Эта функция не умножает уже округлённый первый порог.

Проверочные примеры: `10.1 / 20.2 → 11 / 21` тиков; близкие `10.1 / 10.11 → 11 / 12`; `0.01 / 0.011 → 1 / 2`. Это примеры проверки округления, не результаты эксперимента. При невозможности представить `suspect + 1` операция завершается ошибкой.

## Идентификаторы и счётчики

[ids.hpp](../include/telemetry/common/ids.hpp) задаёт разные типы `NodeId`, `TaskId`, `HeartbeatSeq`, `AttemptNo` на основе `PositiveId<Tag>`. Допустимы положительные целые до UINT64_MAX; значения разных сущностей не смешиваются неявно. Недопустимого ID по умолчанию нет. `.value()` возвращает исходное целое, сравнение задаёт порядок по значению, `.next()` безопасно возвращает следующий ID/номер без изменения исходного объекта.

[checked_integer.hpp](../include/telemetry/common/checked_integer.hpp) проверяет целые до преобразования и содержит `checked_increment`: поколения и технические счётчики могут начинаться с 0, но переполнение и отрицательный вход отклоняются. Детектор хранит отсутствие реального контакта отдельно; внутреннее начальное last_sequence=0 обозначает отсутствие принятого сообщения. Настоящий HeartbeatSeq всегда положителен.

Ошибки: `invalid_argument` для недопустимых входов/отрицательного результата, `overflow_error` для выхода за представимый диапазон, `underflow_error` для потери положительной вычисляемой обработки до нуля. IO добавляет контекст файла/поля к ошибкам входа. Отсутствующий срок за горизонтом — нормальный `nullopt`, не исключение.

## Точность и проверки

Временные сравнения и выбор LL не используют численного допуска. Допуск независимой проверки сумм Load определён в контракте; реализация Load описана в [scheduling.md](scheduling.md). Округление не вычитает epsilon: значение непосредственно выше целого округляется к следующему тику.

[common_tests.cpp](../tests/common_tests.cpp) выполняет три группы CTest: `common_time`, `common_numeric`, `common_ids`. Проверяются целочисленные границы, запреты смешения типов, безопасная арифметика и горизонт, `optional`, ceil и положительная обработка короче тика, NaN/inf, переполнение и underflow, близкие пороги, сохранение raw-диагностики, положительные ID и переполнение номеров/счётчиков. Проверки поведения выполняются явно и не отключаются через NDEBUG; `static_assert` используется только для контрактов типов и constexpr.

Общая библиотека не зависит от JSON, ядра, движка и физической среды. Ядро и движок зависят только от common. Исходные численные проверки зафиксированы в [отчёте этапа 2](stage_2_audit.md), итоговые проверки — в [этапе 14](stage_14_audit.md), воспроизведение передачи — в [этапе 15](stage_15_audit.md).
