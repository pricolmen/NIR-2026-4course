# Этап 3: логические задачи и самоаудит

Дата: 19 октября 2026, Europe/Moscow. Этап 4 не начат.

## Реализовано

[TaskStore](../include/telemetry/core/task_store.hpp) хранит реестр поступивших задач, общую FIFO, историю логических попыток, optional-номер актуального назначения и optional-время единственного принятого завершения. [Общие сообщения](../include/telemetry/common/messages.hpp) описывают задачу, команду назначения и тройку результата. [Наблюдатель аудита](../include/telemetry/core/audit.hpp) получает типизированные события поступления, назначения, отзыва и решения по результату без файловой/JSON-зависимости ядра.

Назначение снимает голову FIFO, сохраняет исходную работу/момент поступления и создаёт первую либо следующую проверенную попытку. Отдельный примитив отзыва снимает актуальность и возвращает задачу в хвост FIFO. Приём результата проверяет всю тройку `(task_id, attempt_no, node_id)`, отмечает принятое завершение и удаляет актуальность одним логическим действием. Старый результат не принимается ни до, ни после переназначения; дубликат принятого результата не меняет состояние и число завершений.

Core стал компилируемой библиотекой с зависимостью только от common. Добавлены [пять групп тестов](../tests/task_store_tests.cpp), [описание состояния/API](task_state.md), точечные исключения документов в `.gitignore`; обновлены README, карта реализации в контракте и номер этапа в CLI/метаданных. [Реализация](../src/core/task_store.cpp) не читает скрытое состояние узла, не включает движок, не работает с файлами и не использует случайность.

## Проверки и результаты

| Группа CTest | Наблюдаемые последствия |
|---|---|
| `tasks_queue` | FIFO сохраняет порядок наблюдений, назначение убирает задачу из общей очереди, несколько назначений не ждут завершений, пустая очередь не создаёт попытку, данные входного объекта и разных экземпляров не разделяются |
| `tasks_results` | Неизвестная задача, неверная попытка и неверный узел отклоняются без изменения реестра; актуальный результат принимается; дубликат не меняет историю/счётчики; завершённый ID нельзя повторно зарегистрировать; optional-время 0 действительно присутствует |
| `tasks_retries` | Отзыв добавляет задачу после уже ожидающих; повторный отзыв не дублирует очередь; старый результат отклоняется без текущего назначения и после нового; три попытки сохраняют исходную работу/поступление, даже при возврате на прежний узел |
| `tasks_inputs` | Неконечная/неположительная работа, несовпадающее поступление, дубликаты и время назад отклоняются; неизвестный отзыв даёт ошибку; неверные операции не меняют состояние, журнал или внутреннее время |
| `tasks_audit` | Типы, порядок и поля событий соответствуют реальным решениям; наблюдатель видит уже целостное состояние; исключения журнала передаются наружу после поступления и принятия результата; повторный вход с изменением состояния запрещён |
| 11 регрессионных тестов | Типы времени/ID, численные границы, JSON, метаданные и CLI сохраняют поведение с актуальным номером этапа 3 |

Все поведенческие проверки явные и работают при NDEBUG. Реестр, очередь и история сравниваются целиком там, где требуется доказать отсутствие изменения от старого/неверного результата. Баланс и уникальность проверяются независимо методом `validate_invariants`; `Recorder` вызывает эту проверку также из callback после каждого события.

## Самоаудит

Проверены критерий этапа 3 и применимые правила попыток/результатов из разделов 4.1, 6.1, 6.6, 9.1 и 12 плана. Дубликат результата не создаёт второе завершение, потому что проверяется завершённость до записи и дальнейшее текущее назначение отсутствует. Отзыв отдельно фиксирует старую попытку и снимает актуальность до возврата наблюдателю; новая выдача берёт номер из неизменённой истории через безопасный `next()`. Полная работа хранится в исходном описании и копируется в каждую команду.

В ходе самоаудита усилены независимая проверка хронологии «прежний отзыв → новое назначение» и тесты ошибки журнала после принятия результата. Для возврата память очереди выделяется до изменения назначения; при поступлении предусмотрен откат очереди при ошибке вставки в map; назначение сначала добавляет запись попытки и только затем снимает очередь. Наблюдатель вызывается после завершения логической операции, ошибки записи не проглатываются и не обозначаются успехом запуска. Это логическая целостность состояния, а не транзакция с внешним журналом.

Проверяются compile_commands.json (C++20, предупреждения, NDEBUG, санитайзеры), отсутствие JSON в командах компиляции core/его теста, CMake-граница `core → common`, локальные Markdown-ссылки, форматирование и `git diff --check`. Применимых AGENTS.md в репозитории и родительских каталогах не найдено. Содержательных противоречий с моделью плана не выявлено.

Это самоаудит основного агента без субагента; независимый аудит по согласованному плану назначен после этапов 10 и 14. Фактические модель/уровень усилий не объявляются подтверждёнными настройками запуска.

## Границы

Узел для назначения передаёт вызывающий код: стратегии RR/LL, Load и каталог производительностей относятся к этапу 4. Совместная сортировка возврата нескольких FAILED, однократность реконфигурации узла и физическая среда не реализованы. Примитив отзыва одной задачи нужен уже сейчас для содержательной проверки повторной попытки; он не принимает FAILED/crash и не отменяет физическую работу. Статус фактического выполнения попытки ядру неизвестен.

Ошибка наблюдателя означает фатальную ошибку запуска; продолжение после неё не поддерживается. Искусственное исчерпание памяти и фактические UINT64_MAX попыток не моделировались; граница базового номера проверена на этапе 2. Linux/GCC/Windows и интеграция с ещё отсутствующим движком не проверены. Журнал JSONL и метрики относятся к следующим этапам; научные результаты не получены.

План и DOCX не изменяются; отчёты предыдущих этапов сохраняются. Коммит и staging не выполнялись. На этапе 3 работа останавливается.
