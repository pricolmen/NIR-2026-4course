# CLI и сравнение: этап 12

Исполняемый файл telemetry_sim принимает команды из [README](../README.md). Глобальные --help, --version и --build-info работают без команды; <command> --help показывает синтаксис. Все флаги команды должны быть известны, указаны один раз и иметь требуемое значение. Имена команд/вариантов чувствительны к регистру. Позиционные аргументы, сокращения флагов и форма --key=value не поддерживаются. Пути с пробелами следует заключать в кавычки оболочки.

| Команда | Обязательные параметры | Результат |
|---|---|---|
| validate | --scenario FILE | Проверка JSON/CSV, число узлов/задач и горизонт; без моделирования/выходных файлов |
| run | --scenario FILE --detector fixed/adaptive --scheduler rr/ll --out DIR | Один запуск со всеми файлами этапа 11 |
| compare | --scenario FILE --out DIR | Четыре подкаталога и comparison.csv |
| metrics | --run-dir DIR | Независимый пересчёт metrics.json и трёх CSV по сохранённым input/* и events.jsonl |
| generate | --config FILE --out DIR | Сохранённый scenario.json/delivery.csv и метаданные генератора |
| batch | --manifest FILE --out DIR | Сравнение сохранённых сценариев и comparison.csv/summary.csv |

run/compare/generate/batch принимают --overwrite. У metrics это отдельная явно запрошенная регенерация производных отчётов; флаг --overwrite ей не нужен. metrics принимает каталог отдельного запуска, например results/comparison/fixed_rr, а не корень compare или batch. Алгоритмы и определения метрик: [контракт](model_contract.md), [журнал/метрики](journal_metrics.md).

Коды: 0 — успех, включая корректно учтённые незавершённые задачи; 2 — синтаксис CLI, неизвестная команда/флаг, повтор/пропуск параметра или неверный выбор детектора/планировщика; 1 — входные данные, запись, несогласованный журнал, техническая/численная ошибка. Неполное моделирование не выдаётся за нормальный горизонт. --build-info теперь содержит simulation_available=true, платформу и стандартную библиотеку.

## Выходные каталоги и замена

CLI вычисляет результат в отдельном соседнем .<name>.work-N. Только после успешного выполнения он переименовывается в запрошенный DIR. При обычном исключении временный каталог очищается, прежний результат не меняется. Непустой DIR без --overwrite отклоняется. При явной замене прежний каталог сохраняется рядом как .<name>.previous-N, путь печатается. Резервные каталоги автоматически не удаляются.

Запрещено заменять корень, текущий рабочий каталог/его предков, каталог с используемыми входами или конечную ссылку symlink. Проверяются также CSV сценария и все входы batch, с нормализацией путей. Обычные файлы на месте DIR не заменяются. Пустой существующий каталог также может быть сохранён как предыдущий. При ошибке финального rename выполняется попытка вернуть прежний каталог из backup. Аварийное завершение процесса между двумя rename может оставить прежний результат под именем backup; полной транзакции файловой системы не заявляется. Одновременные запуски в один DIR и конкурентное редактирование входов не поддерживаются.

## Четыре варианта и общий CSV

write_comparison из [run_output.hpp](../include/telemetry/io/run_output.hpp) сначала сохраняет общий input/scenario.json и input/delivery.csv и загружает один const Scenario. Один shared_ptr передаётся новым Simulation для fixed_rr, fixed_ll, adaptive_rr, adaptive_ll в этом порядке. Каждая Simulation владеет своим изменяемым состоянием. Повторного чтения/генерации сети между вариантами нет. Снимки общих входов дополнительно копируются внутрь каждого запуска для его независимого переноса и пересчёта. Общий comparison_manifest.json получает complete после успеха всех вариантов и CSV.

comparison.csv содержит одну строку на вариант и окно измерения: счётчики, средние latency/Detection/Recovery, P95, числа наблюдений, границы и throughput. Без окон сохраняется одна строка с пустыми полями окна и throughput_reason=no_measurement_window. Отсутствующие средние/P95 имеют пустую ячейку и empty_sample. Поля времени — тики, throughput — задачи/с. CSV корректно экранирует кавычки, запятые и переносы строк в метках. Агрегатные счётчики повторяются для каждой строки окна; их нельзя суммировать по строкам разных окон.

## Генератор версии 1

Готовая небольшая конфигурация: [examples/generator.json](../examples/generator.json). Это демонстрационные параметры, не научно обоснованная серия. Все поля обязательны, неизвестные поля и дубликаты запрещены:

| Поле | Смысл и диапазон |
|---|---|
| schema_version | 1 |
| seed | Целый uint64, включая 0 и UINT64_MAX; без bool/дроби/экспоненты |
| scenario | tick_ns=1000, horizon_ticks, heartbeat_period_ticks, tau0_ticks, kappa, adaptive, nodes, crashes, blackouts, measurement_windows с семантикой сценария |
| tasks.count | Неотрицательное число задач; ID генерируются от 1 |
| tasks.first_arrival_ticks | Неотрицательное первое поступление до горизонта |
| tasks.period_ticks | Положительный период; последнее поступление должно помещаться в горизонт |
| tasks.work_min/work_max | Конечные положительные границы min<=max; равенство задаёт постоянную работу |
| delivery.min_delay_ticks/max_delay_ticks | Целые неотрицательные границы min<=max |
| delivery.loss_probability | Конечное q из [0,1]; 0 — без потерь, 1 — потеря всех сообщений |

scenario не содержит tasks, schema_version или delivery_trace: их записывает генератор. Каталог scenario.nodes обязан содержать хотя бы один узел, даже при tasks.count=0. Настройки, численные диапазоны, ссылки, crash/перерывы/окна проверяются до начала записи. Используется общий строгий SAX-читатель nlohmann/json с long double, без промежуточного double, целые тики не округляются. Сначала генерируются задачи по ID, затем потенциальные heartbeat по возрастанию ID узлов и номера сообщения, включая отправки после crash. Генератор не моделирует исполнения.

RNG — mt19937_64. Работа — uniform_real_distribution<long double>, либо константа без случайного выбора; задержки — uniform_int_distribution<int64_t>; потеря — сравнение отдельного uniform_real<long double> с q, крайние q проверяются явно. Сохранённый сценарий повторно загружается и валидируется перед публикацией. generation_manifest.json содержит generator_version=1, seed, распределения, контрольные суммы, компилятор/платформу/стандартную библиотеку; generator_config.json сохраняет точные байты настроек.

Один seed даёт повторяемые файлы в одной программной среде, но не обещает побитового совпадения стандартных распределений разных библиотек. Основание compare/batch — сохранённые входы. run и compare вообще не вызывают RNG. На этапе 13 добавлены [полный каталог демонстраций](../examples/README.md) и сохранённый контроль generator_recovery.json; повторная генерация/загрузка проверены отдельно.

## Batch и сводка повторов

Формат [examples/experiments.json](../examples/experiments.json):

```json
{
  "schema_version": 1,
  "runs": [
    {"scenario_id": "baseline", "repeat_id": "manual_1", "scenario": "baseline/scenario.json"}
  ]
}
```

Пути сценариев разрешаются относительно manifest. runs непуст, все поля обязательны; scenario_id/repeat_id — непустые строки без NUL, пара уникальна. Все входы предварительно валидируются. Метки не используются как компоненты пути: выходы — runs/000001, runs/000002 и далее, в порядке scenario_id/repeat_id. Каждый элемент запускает compare на своих сохранённых входах, без генерации. batch_manifest.json связывает метки с каталогами и получает complete после всех запусков/таблиц.

comparison.csv сохраняет метрики каждого повтора. summary.csv группирует scenario_id, variant, window_index и границы окна. Разные окна не усредняются молча. Для каждой метрики сводка хранит среднее по определённым значениям запусков, число этих запусков и причину пустого среднего. Сначала рассчитываются mean latency и P95 каждого запуска, затем отдельно усредняются; P95 объединённой выборки не вычисляется. Для Detection/Recovery дополнительно выводятся суммы определённых узловых наблюдений — они не служат весами среднего по запускам. FP/FN, поздние crash, незавершённые Recovery и задачи сохраняются отдельными totals. Строки разных окон повторяют эти totals.

Отдельная проверка даёт mean_run_detection=16.75 при двух определённых запусках и трёх отказах; это отличается от объединённого среднего по трём отказам. Размеры выборок явно видны. Одиночный повтор или одинаковые повторно прочитанные входы служат технической проверкой, а не статистическим доказательством.
