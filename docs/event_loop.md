# Универсальный движок событий

Этап 7: [event_loop.hpp](../include/telemetry/engine/event_loop.hpp), [event_loop.cpp](../src/engine/event_loop.cpp). Движок зависит только от common. Номера фаз и числовые ключи непрозрачны для него; правила конкретной модели задаёт адаптер. Действия — `std::function<void(EventLoop&)>`, вызываемые последовательно в одном потоке.

## Ключ и очередь

Минимальный ключ — `(SimTime, Phase, TieKey, insertion_sequence)`. Phase — положительное целое uint64 с явным проверяемым конструктором: отрицательные значения и 0 отклоняются, bool/вещественные типы не принимаются. Ограничение восемью фазами будет правилом адаптера, а не универсального движка.

TieKey — массив четырёх uint64, сравниваемых лексикографически. Неиспользуемые компоненты заполняются нулями. Четырёх компонент достаточно для будущих ключей узла/задачи/попытки и узла/вида проверки/поколения. Их смысл и канонический порядок задаёт адаптер; адреса объектов и порядок hash-таблиц не используются.

Порядковый номер вставки начинается с 1 и увеличивается только при успешной постановке. Полное равенство времени, фазы и TieKey разрешается этим номером. Он проверяется на переполнение до изменения очереди. Структура EventKey доступна для диагностики и возвращается при постановке; задать внутренний порядковый номер через API нельзя.

Очередь — двоичная куча в vector, компаратор сравнивает только ключи. Добавление и извлечение требуют O(log E) сравнений, память — O(E) плюс данные действий. Расширение vector иногда переносит O(E) элементов; амортизированная стоимость добавления остаётся O(log E). Текущее действие извлекается в отдельный объект до вызова, поэтому добавление новых событий и перераспределение vector не уничтожает выполняемый callback.

## Планирование и время

`EventLoop(horizon)` создаёт экземпляр без технического лимита. Второй целочисленный аргумент задаёт максимальное число выполненных действий; отрицательное значение отклоняется, bool/дробный аргумент не принимаются. Горизонт может быть нулевым для нейтральных проверок; положительный горизонт файла сценария проверит загрузчик на этапе 9.

`now()` сначала равен 0. `schedule(at, phase, key, action)` ставит абсолютное событие; `schedule_after(delay, phase, key, action)` использует текущее модельное время. Оба возвращают optional EventKey. Пустое действие является ошибкой даже для срока за горизонтом. Событие строго за горизонтом возвращает nullopt, не хранится и не расходует номер вставки. Срок на горизонте включается.

Относительный срок вычисляется через `deadline_within`, сравнивающий delay с оставшимся временем до сложения. Поэтому даже огромная задержка рядом с INT64_MAX безопасно пропускается за горизонтом. Никаких системных часов, ожиданий или прохода по тикам нет.

Во время исполнения нельзя ставить событие раньше now. В той же отметке разрешена только фаза строго больше текущей; текущая фаза запрещена независимо от TieKey. Нулевая задержка в следующую фазу допустима. В более поздней отметке разрешена любая положительная фаза. До run можно поставить любое событие от 0 до горизонта включительно. Обработчик при необходимости исполняет мгновенное следствие синхронно или планирует последующую фазу.

## Запуск и ошибки

Состояния — ready, running, completed, failed. `run()` вызывается ровно один раз, в том числе после ошибки. Вложенный run запрещён. Экземпляр не копируется и не перемещается, чтобы не дублировать исполняемые действия и ссылки их захватов. Ссылки в захватах действий должны оставаться действительными до исполнения или уничтожения очереди.

Перед callback обновляются now и last_event. После успешного callback увеличивается executed. last_event хранит ключ последнего вызванного действия, включая действие, выбросившее исключение; executed считает только завершившиеся действия. pending показывает число ещё не извлечённых событий. Движок не хранит полную историю исполнения.

Когда очередь пуста, now становится равным горизонту без создания дополнительного события, состояние — completed, возвращается RunResult с достигнутым временем и числом действий. Поэтому пустой запуск корректно достигает горизонта, а last_event у него отсутствует.

Исключение, вышедшее из действия, распространяется наружу и устанавливает failed. Позднейшие события не исполняются, очередь остаётся для диагностики, нормальный RunResult не возвращается. Ранее совершённые внешние изменения действия не откатываются. Ошибку запрещённой вставки можно явно обработать внутри самого действия: отклонённая постановка сохраняет очередь и счётчик. Необработанная ошибка прекращает запуск. После completed/failed планирование запрещено.

Технический лимит проверяется до извлечения следующего события. Если число действий уже достигло лимита и очередь непуста, выбрасывается EventLimitExceeded и сохраняется failed. Это действует даже при now == horizon: необработанные последующие фазы на горизонте означают неполный запуск. Если очередь опустела ровно на лимите, запуск успешен. Лимит 0 допустим только для пустого запуска. Это ограничение числа событий, а не времени исполнения отдельного callback.

Все выделения памяти постановки происходят до изменения кучи/счётчика. Перемещения событий и компаратор не выбрасывают исключений. Ошибка подготовки постановки оставляет очередь целостной; искусственное исчерпание памяти не тестировалось. Переполнение счётчиков проверяет общий checked_increment; достижение UINT64_MAX событий в рабочей очереди не воспроизводилось.

## Проверки и границы

Шесть групп [engine_tests.cpp](../tests/engine_tests.cpp) проверяют порядок всех частей ключа, равенство ключей и FIFO вставок, динамическую постановку, монотонность и запрет текущей фазы, нулевую задержку, включённый горизонт и INT64_MAX, ошибки действий, однократность run, лимиты и повторяемость. Тесты связаны только с engine/common; классы детекторов и распределения не используются.

Восемь фаз, их предметные имена, пропуски устаревших физических событий/таймеров, объединение реконфигурации и dispatch — обязанности будущего адаптера. [Физическая среда](physical_environment.md) реализована отдельно на этапе 8, полный адаптер ядра относится к этапу 10. Движок не удаляет старые поколения по их смыслу: соответствующее действие проверит токен и запишет диагностический пропуск. Фактические результаты сборок и самоаудит — в [stage_7_audit.md](stage_7_audit.md).
