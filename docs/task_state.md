# Логические задачи, назначения и попытки

Реализация этапа 3: [TaskStore](../include/telemetry/core/task_store.hpp), [код](../src/core/task_store.cpp), [общие сообщения](../include/telemetry/common/messages.hpp), [события аудита](../include/telemetry/core/audit.hpp). Правила задаёт [контракт модели](model_contract.md).

## Состояние и операции

`TaskStore` владеет реестром только уже поступивших задач, общей FIFO, историей логических попыток и единственным актуальным номером попытки каждой назначенной задачи. У задачи сохраняются исходные ID, момент поступления и полная работа. Внешние команды содержат копию описания, изменение входного объекта не меняет реестр. Доступ к реестру/очереди снаружи только для чтения. Store не копируется, варианты запуска создают собственные экземпляры; наблюдатель принадлежит вызывающему коду.

| Операция | Поведение |
|---|---|
| `arrive(at, task)` | Требует совпадения наблюдаемого времени с исходным поступлением, конечной положительной работы и нового ID; добавляет задачу в хвост FIFO |
| `assign_next(at, node)` | Если очередь непуста, снимает её голову, создаёт попытку 1 или следующую и возвращает команду; при пустой очереди возвращает `nullopt` |
| `receive_result(at, result)` | Принимает только текущую тройку задача/попытка/узел незавершённой задачи; иначе возвращает причину отклонения |
| `revoke_assignment(at, task_id)` | Примитив отзыва одного актуального назначения: помечает попытку, убирает актуальность и добавляет задачу в хвост FIFO; повторный отзыв/отзыв завершённой задачи возвращает false |
| `counts()` | Вычисляет числа поступивших, завершённых, ожидающих и назначенных по текущему состоянию за O(N); отдельного изменяемого счётчика принятия нет |
| `validate_invariants()` | Независимо проверяет баланс, множества и историю; предназначен для тестов/аудита, не вызывается на каждой операции рабочего запуска |

Выбор исполнителя пока задаёт вызывающий код. Каталога узлов, ALIVE/SUSPECT/FAILED, Load и проверки принадлежности NodeId сценарию в TaskStore нет: эти условия проверяет Dispatcher, а оценки наблюдений — Detector. NodeId уже гарантирует положительный целый ID. Назначение не проверяет занятость узла, поэтому вручную можно выдать несколько задач одному узлу до получения любого результата.

FIFO сохраняет порядок наблюдений, не сортирует входящие задачи самостоятельно. В будущем адаптер подаст поступления одной отметки по ID. Примитив отзыва сохраняет существующую очередь и добавляет одну возвращённую задачу в конец. Он не является совместной реконфигурацией: на этапе 6 [Dispatcher](reconfiguration.md) готовит общий набор нескольких узлов, сортирует его по исходному поступлению/ID и применяет всю пачку до callback, а dispatch вызывается отдельно.

Все изменения используют явно переданное время. Наблюдения одного экземпляра не убывают; равные времена допустимы. Некорректный вход и неизвестный ID в отзыве не изменяют состояние или время последнего наблюдения. Отклонённый результат является обработанным наблюдением и продвигает это время, но не меняет реестр задач, попытки и их счётчики. Пустая выдача и повторный отзыв также учитывают время вызова. Физические фазы и минимальную длительность обработки обеспечит среда: ядро не пытается восстановить их по скрытым данным.

## Защита результата

Порядок решения стабилен: неизвестная задача → уже завершённая → нет текущего назначения → неверная попытка → неверный узел → принято. Принятие без выделения памяти и вызова наблюдателя между обновлениями одновременно фиксирует время принятия попытки, завершает задачу и убирает актуальное назначение. Повторный результат не создаёт второе завершение.

Отозванный результат отклоняется и до нового назначения, и после него. Даже если новый исполнитель совпадает с прежним, номер попытки обязан совпасть с актуальным. Новая попытка использует полную исходную работу и следующий проверенный `AttemptNo`; старая история сохраняется. Отсутствующие моменты — optional, а присутствующее время 0 не считается отсутствием.

Логическая попытка содержит номер, узел, момент назначения, optional-моменты отзыва и принятия. Физических начала/завершения, прогресса обработки и отмены здесь нет. Отзыв не посылает команду физической отмены и не очищает локальную очередь среды. Снятие Load и совместная однократная реконфигурация относятся к этапам 4 и 6 соответственно.

## Аудит и ошибки

`AuditSink::on_event` получает вариант одного из событий: поступление, назначение, отзыв, решение по результату; Dispatcher дополнительно выдаёт единый ReconfigurationEvent для пачки доступности/отзывов. У события явное модельное время и типизированные поля, у результата — `ResultDecision`. Ссылка действительна на время callback; наблюдатель копирует данные или пишет их синхронно. TaskStore не накапливает журнал. Сквозной номер записи, фаза и JSONL добавятся внешним журналом/адаптером позднее.

Наблюдатель вызывается после полного обновления состояния, может читать его, но не может повторно вызвать изменяющую операцию: такая реентерабельность запрещена. Ошибка наблюдателя распространяется вызывающему коду и означает ошибочный запуск; она не откатывает уже записанные внешние данные или совершённое логическое действие. Продолжать моделирование после неё нельзя. Проверки подтверждают, что даже при ошибке записи после принятия результата состояние остаётся целостным.

Выделение памяти при поступлении/назначении/возврате выполняется до необратимого обновления логического состояния либо с локальным откатом. Искусственное исчерпание памяти не тестировалось. Переполнение номера попытки проверяет `AttemptNo::next()` до изменения реестра; само достижение UINT64_MAX попыток в TaskStore не моделировалось, граница базового типа покрыта этапом 2.

Инварианты: каждый известный ID ровно в одном из состояний «FIFO», «актуальное назначение», «завершён»; очередь не имеет дубликатов; активная попытка одна и последняя; номера последовательны; все прежние попытки отозваны до следующего назначения; принятый результат максимум один и у последней попытки. Выполняется `N_in = N_done + N_queued + N_assigned`, где `N_in` — только поступившие задачи.

Пять групп [тестов](../tests/task_store_tests.cpp) — `tasks_queue`, `tasks_results`, `tasks_retries`, `tasks_inputs`, `tasks_audit` — работают без движка, JSON и файлов сценария. В тестах используются ручные времена, узлы и результаты; это не физический запуск симуляции и не исследовательские результаты. Фактические проверки и границы самоаудита — в [отчёте этапа 3](stage_3_audit.md).

На этапе 4 добавлен [Dispatcher](scheduling.md): для согласованного учёта Load операции рабочего ядра идут через эту обёртку; доступ к её TaskStore только константный. Сам TaskStore остаётся отдельным компонентом без нагрузки и стратегий.

На этапе 6 подготовка и применение совместного отзыва добавлены как private-механизм координации с Dispatcher. Существующий одиночный отзыв сохранён; он не заменяет применение FAILED. Поведение и границы — в [reconfiguration.md](reconfiguration.md).
