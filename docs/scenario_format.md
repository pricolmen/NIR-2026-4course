# Загрузка сценария JSON/CSV

Этап 9: [load_scenario](../include/telemetry/io/scenario_loader.hpp), [загрузчик](../src/io/scenario_loader.cpp), [неизменяемый Scenario](../include/telemetry/simulation/scenario.hpp) и [проверки модели](../src/simulation/scenario.cpp). Примеры: [baseline](../examples/baseline/README.md), [crash](../examples/crash/README.md), [blackout](../examples/blackout/README.md).

## API и владение

```cpp
auto loaded = telemetry::io::load_scenario("examples/baseline/scenario.json");
const auto& scenario = *loaded.scenario;
// scenario.physical(), timeout(), adaptive(), tasks(), measurement_windows()
```

LoadedScenario содержит shared_ptr<const Scenario> и абсолютные лексически нормализованные пути JSON/CSV. Путь delivery_trace разрешается относительно родительского каталога переданного JSON, а не cwd. Поддержаны пробелы/Unicode, переходы `../` и абсолютный путь CSV; для переносимых примеров используется относительный. Файлы только читаются. Пустые пути и NUL отклоняются.

Scenario хранит общую const PhysicalTrace, параметры детекторов, задачи в каноническом порядке `(arrival,id)` и окна измерения в порядке входа. Изменяющих методов и присваивания нет. Каждый запуск должен создавать собственные Dispatcher, Detector, EventLoop и PhysicalEnvironment поверх этих данных. Тесты подтверждают независимость физических состояний и неизменность файлов; полный запуск четырёх вариантов относится к следующим этапам.

## JSON версии 1

Все поля ниже обязательны. Неизвестные поля и повторные ключи отклоняются на любом уровне. Массив nodes должен содержать хотя бы один узел, независимо от числа задач. tasks, crashes, blackouts и measurement_windows могут быть пустыми. Во время моделирования все исходные узлы могут стать недоступными; такая незавершённость учитывается штатно.

| Поле | Ограничения |
|---|---|
| schema_version | Целое 1 |
| tick_ns | Целое 1000; один тик — микросекунда |
| horizon_ticks | Целое 1..INT64_MAX |
| heartbeat_period_ticks | Целое H > 0 |
| tau0_ticks | Целое tau0 >= H, не выше INT64_MAX |
| kappa | Конечное число > 1; исходные и округлённые начальные пороги представимы |
| adaptive | window >= min_intervals >= 2 — целые в пределах size_t; c — конечное число >= 0 |
| nodes | Непустой массив объектов id и performance_work_per_second; ID уникален, производительность конечна и > 0 |
| tasks | Объекты id, arrival_ticks, work; ID уникален, 0 <= arrival <= horizon, work конечна и > 0 |
| crashes | Объекты node_id и at_ticks; известный узел, не более одного crash на узел, 0 <= at <= horizon |
| blackouts | Объекты node_id, start_ticks, end_ticks; известный узел, неотрицательный start < end; выход за горизонт допустим |
| measurement_windows | Объекты start_ticks, end_ticks; 0 <= start < end <= horizon |
| delivery_trace | Непустая строка пути к CSV |

Положительные ID используют весь диапазон uint64. Для времён и целых параметров требуется именно целочисленный JSON-токен. `1.0`, `1e0`, bool, строки, отрицательные значения и переполнение не принимаются как целые. Значения не проходят через double. Нулевой момент задачи/crash сохраняется как действительное время.

Работа, производительность и коэффициенты читаются как long double. Грамматику/токены разбирает nlohmann/json 3.12.0 через публичный SAX API; callback собирает DOM этой библиотеки и проверяет дубликаты и потерю ненулевой величины до нуля. Собственного лексического или синтаксического JSON-парсера нет. NaN/inf не допускаются, включая переполнение экспоненты. Точность остаётся точностью long double проверенной платформы; это не произвольная десятичная арифметика.

Начальные пороги проверяются общим round_thresholds. Для каждой работы проверяется processing_duration на минимальной и максимальной производительности: этого достаточно для границ монотонной формулы w/p без проверки всех пар задач/узлов. Динамические суммы Load и будущие адаптивные пороги всё равно проверяются во время запуска; валидный файл не гарантирует отсутствие всех будущих численных ошибок.

Содержательные инварианты также проверяет конструктор Scenario для входа в памяти; параметры детектора проверяются существующим Detector, без второй машины состояний. Пересекающиеся/соседние перерывы объединяет PhysicalTrace. Повторяющиеся окна измерения не запрещены: отдельного требования уникальности в плане нет.

## CSV доставки

Обязательный заголовок и числовые строки:

```csv
node_id,heartbeat_seq,delay_ticks,lost
1,1,0,0
1,2,3,1
```

Ровно четыре столбца в указанном порядке. Поля содержат десятичные цифры; у node_id/heartbeat_seq значение положительно, у delay_ticks — 0..INT64_MAX. Дробь, экспонента, знак и переполнение отклоняются. lost — ровно 0 или 1. Поддержаны LF/CRLF, BOM заголовка, пробелы/табуляция вокруг полей и последняя строка без перевода строки. Профиль состоит только из числовых полей: CSV-кавычки, комментарии, дополнительные столбцы и пустые строки не поддерживаются.

Для каждого исходного узла требуется ровно по одной строке с heartbeat_seq = 1..floor(horizon/H). Это включает потенциальные отправки после crash. При horizon < H требуется только заголовок. Порядок строк произвольный, дубликаты и неизвестные узлы запрещены. Проверка полноты не перечисляет отсутствующие номера: диапазон, уникальность и число записей доказывают полноту. Поэтому огромная неполная трасса быстро отклоняется по прочитанному объёму. Доставка за горизонтом допустима и не переполняет сложение в среде.

## Ошибки и проверки

InputError содержит файл и JSON-путь поля, CSV-строку/столбец или байт синтаксической ошибки JSON. Примеры:

```text
.../scenario.json: $.tasks[0].arrival_ticks: beyond horizon
.../delivery.csv: line 6, node_id/heartbeat_seq: duplicate key first seen on line 5
```

Отсутствующая строка описывается через node_id/heartbeat_seq и ожидаемое/прочитанное число строк. Ошибка открытия CSV указывает разрешённый абсолютный путь. Неверный вход не исправляется значениями по умолчанию и не даёт частично готового LoadedScenario. Выделение памяти может завершить вызов исключением; искусственное исчерпание памяти не проверялось.

JSON остаётся приватной зависимостью IO и его тестов. IO теперь зависит от simulation с нативным Scenario; обратных зависимостей у core/engine нет. Шесть групп [scenario_tests.cpp](../tests/scenario_tests.cpp) проверяют корректные/неисправные входы, относительные пути, крайние числа, независимые состояния и три примера. Данные тестов создаются внутри каталога сборки.

Загрузчик этапа 9 используется библиотечным [адаптером этапа 10](simulation.md). Сквозные прогоны сохранённых примеров проверены CTest. Команды validate/run/compare реализованы на [этапе 12](cli.md), simulation_available=true. Результаты загрузчика — в [stage_9_audit.md](stage_9_audit.md), интеграции и независимого аудита — в [stage_10_audit.md](stage_10_audit.md). Примеры не являются исследовательскими выводами.

На этапе 11 добавлена перегрузка `load_scenario(file, delivery_override)` для переносимых снимков результатов. Она валидирует исходное поле delivery_trace, но использует явно переданный CSV, сохраняя байты JSON и точность чисел. Все прежние проверки входов сохраняются. Сохранение и пересчёт — в [journal_metrics.md](journal_metrics.md).
