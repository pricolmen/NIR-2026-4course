# Воспроизведение запусков и сравнения

Документ описывает работу с реальными сохранёнными входами и выходами стенда. Сборка и первый запуск — в [README](../README.md), точные форматы — в [scenario_format.md](scenario_format.md), [cli.md](cli.md) и [journal_metrics.md](journal_metrics.md). Здесь используется `build/final-release/telemetry_sim`; команды выполняются из корня проекта.

## Контроль перед сравнением

Сначала выполните baseline из README. Два одинаковых узла, четыре задачи работы `[4,2,4,2]` при поступлении 0, горизонт 20. Для RR ожидаются завершения `[4,2,8,4]`, mean latency 4.5, P95 8 тиков и throughput 200000 задач/с в `(0,20]`. Для LL завершения `[4,2,6,6]`, mean latency 4.5, P95 6. В отсутствие нарушений детекторы не меняют эти результаты. Это проверка соответствия реализации ручному примеру, а не оценка научного эффекта.

[Каталог](../examples/README.md) содержит девять сохранённых случаев: baseline, crash, краткий blackout, длительный ложный FAILED, перестановку сообщений, одновременные исключения, отсутствие ALIVE, незавершённость и результат генератора с ручным Recovery. Чтобы отдельно просмотреть ложное исключение:

```sh
./build/final-release/telemetry_sim compare --scenario examples/long_blackout/scenario.json --out results/final-long-blackout
./build/final-release/telemetry_sim metrics --run-dir results/final-long-blackout/fixed_rr
```

Смотрите `nodes.csv` для классификации, `attempts.csv` для отзывов и поздних результатов, `events.jsonl` для точного порядка фаз. Ожидания каждого случая описаны рядом с его входами. Пустые значения метрик имеют причину; их нельзя заменять нулём.

## Материализация собственного опыта

1. Подготовьте конфигурацию по `examples/generator.json` или `generator_recovery.json`. Явно задайте seed, узлы/p, горизонт, H, tau0/kappa, M/min_intervals/c, поток работ, задержки/потери, crash/blackout и окна измерения. Работа измеряется в условных единицах, p — в единицах/с.
2. Выполните `generate` в новый каталог. Сохраните его целиком: `generator_config.json`, `generation_manifest.json`, `scenario.json`, `delivery.csv`. Проверьте `validate` и статус manifest.
3. Выполните `compare` на полученном `scenario.json`. Четыре варианта используют один загруженный неизменяемый Scenario и получают независимое состояние. RNG внутри моделирования отсутствует.
4. Сохраните весь каталог сравнения, включая manifest, журналы и `input/` каждого варианта. Повторно выполните `metrics` для нужного варианта. Пересчёт не требует исходного пути сценария и не доверяет старому metrics.json.

Пример технического контроля генератора:

```sh
./build/final-release/telemetry_sim generate --config examples/generator_recovery.json --out traces/experiment-recovery
./build/final-release/telemetry_sim validate --scenario traces/experiment-recovery/scenario.json
./build/final-release/telemetry_sim compare --scenario traces/experiment-recovery/scenario.json --out results/experiment-recovery
./build/final-release/telemetry_sim metrics --run-dir results/experiment-recovery/fixed_rr
```

Здесь ожидаются Detection 5 и Recovery 17 тиков. Входы должны совпасть с `examples/generated_recovery/{scenario.json,delivery.csv}`. Этот контроль использует константные работу/задержку и q=0. Для произвольных диапазонов один seed гарантирует повтор только в той же программной среде: стандартные распределения могут различаться между библиотеками. Основа воспроизведения — сохранённые JSON/CSV. Для точного повторения сохраняйте также commit исходников, `--build-info`, настройки CMake и компилятор/стандартную библиотеку; manifests уже фиксируют сведения о сборке и входах.

При одинаковых входах в одной сборке ожидается совпадение журнала, metrics и CSV. Manifest дополнительно хранит происхождение и метаданные, поэтому перенос исходных файлов, другой путь или номер этапа могут изменить его байты. Wall-clock время не включается в канонический журнал. FNV-1a-64 manifest служит проверкой целостности, не защитой от намеренной подмены.

## Серия и независимые повторы

`batch` читает уже подготовленный manifest. Для запуска полного демонстрационного каталога:

```sh
./build/final-release/telemetry_sim batch --manifest examples/experiments.json --out results/experiment-suite
```

В manifest каждый элемент имеет уникальную пару `scenario_id`/`repeat_id` и путь `scenario`, разрешаемый относительно manifest. Пример двух заранее сгенерированных повторов одного сценария (это шаблон, не существующие входы поставки):

```json
{
  "schema_version": 1,
  "runs": [
    {"scenario_id": "case_a", "repeat_id": "seed_1", "scenario": "seed_1/scenario.json"},
    {"scenario_id": "case_a", "repeat_id": "seed_2", "scenario": "seed_2/scenario.json"}
  ]
}
```

Для разных независимых повторов заранее сгенерируйте разные сохранённые входы с разными seed. Внутри каждого повтора сравниваются все четыре варианта на одном входе. Повторение одного и того же входа с другой меткой проверяет детерминизм и не добавляет независимых наблюдений.

Выход — `batch_manifest.json`, `runs/000001/...`, общий `comparison.csv` и `summary.csv`. Порядок каталогов задаётся сортировкой ID; соответствие читайте из manifest. Входные метки не используются как имена каталогов. Группировка summary: scenario_id, variant, window_index и границы окна. Среднее рассчитывается по определённым значениям показателя отдельных запусков, а число таких запусков выводится отдельно. Mean latency и P95 сначала вычисляются внутри каждого запуска; среднее P95 не равно P95 объединённых задач. Для Detection/Recovery число узловых наблюдений не используется как вес среднего по запускам. Totals, повторённые в строках разных окон, не нужно суммировать между окнами.

Стенд не рассчитывает доверительные интервалы и не выбирает за исследователя объём выборки, реалистичные параметры или критерий сравнения. Эти решения требуют отдельного обоснования. На демонстрациях по одному техническому повтору каждого случая.

## Интерпретация показателей

| Показатель | Определение и границы |
|---|---|
| Latency | Принятое завершение минус исходное поступление, только уникально завершённые задачи |
| Mean / P95 latency | Среднее; ближайший ранг `ceil(0.95*n)` без интерполяции. Пустая выборка — null/empty_sample |
| Throughput | Число принятых задач в `(start,end]`, делённое на длительность окна в секундах; время 0 не входит в окно с start=0 |
| Detection | Корректный FAILED минус настоящий crash; только определённые наблюдения |
| Recovery | Последнее окончательно принятое завершение фиксированного возвращённого набора R минус crash; пустой R даёт Detection |
| FP / FN | FAILED до/без crash; crash, не обнаруженный до включённого горизонта. Поздний crash после FP выделяется отдельно, без нового Detection/FN |
| Незавершённые Recovery | Если хотя бы одна задача R не завершена, Recovery — null/recovery_incomplete |
| Retries | Каждое назначение после первого: три назначения означают два повтора |

Отдельно смотрите `arrived`, `completed`, `unfinished`, `queued`, `assigned`, размеры выборок Detection/Recovery/latency и причины null. `manifest.status=complete` означает корректное исполнение до горизонта и запись результатов; он не означает завершение всех задач. Сравнение средних при различающихся долях незавершённости требует учитывать эту цензуру.

## Подтверждённые проверки и ограничения

Раздел 12 плана проверен тестами и независимым аудитом: [этап 14](stage_14_audit.md). Нагрузочный smoke использует 6 узлов, 2000 задач, 1920 потенциальных heartbeat, горизонт 8000 тиков, один crash и один blackout. Он проверяет баланс, уникальность принятия, канонические повторы, обратный порядок вариантов и независимый пересчёт. Фактические действия/записи/байты и время находятся в отчёте этапа 14 и `build/stage14-{debug,release,sanitize}/stage14-load/report.json`.

Новый запуск `final_load_smoke` сохраняет тот же отчёт в `stage14-load/report.json` внутри выбранного каталога сборки (имя подкаталога сохранено как имя проверки этапа 14). Эти wall-clock интервалы включают файловую работу и проверку; они не измеряют научное преимущество алгоритмов. Результаты этой версии проверены только на macOS arm64; другие платформы, исчерпание памяти и конкурентная запись не заявляются проверенными. Модель не включает настоящий сетевой обмен, ОС узлов, GUI или потоки реального времени. Глава 3 НИР автоматически не создавалась.
