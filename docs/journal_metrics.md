# Журнал, метрики и отчёты: этап 11

[JournalWriter](../include/telemetry/io/journal.hpp) последовательно пишет events.jsonl из типизированных событий Simulation. [Analyzer](../include/telemetry/metrics/analysis.hpp) независимо восстанавливает логические задачи, физические попытки, оценки узлов и метрики из сценария и потока событий. Он не читает состояние Simulation и не передаёт служебных сведений в алгоритмы. Модуль metrics зависит от simulation, без JSON; сериализация остаётся приватной частью IO.

## Библиотечный API

```cpp
#include "telemetry/io/run_output.hpp"

const auto report = telemetry::io::write_run(
    "examples/baseline/scenario.json",
    telemetry::simulation::Variant::fixed_rr,
    "results/baseline");
const auto recomputed = telemetry::io::analyze_run("results/baseline");
telemetry::io::recalculate_reports("results/baseline");
```

write_run создаёт новый либо использует пустой каталог. Непустой каталог отклоняется; автоматической перезаписи нет. Функция возвращает результат только после успешного моделирования, завершения журнала и записи отчётов. Она использует исходный загрузчик с его строгой проверкой. Все исключения передаются вызывающему; CLI появится на этапе 12.

analyze_run проверяет manifest, контрольные суммы входов/журнала, читает сохранённые входы и потоково анализирует events.jsonl. Она не запускает Simulation и не читает прежние metrics.json/CSV. recalculate_reports выполняет тот же анализ и заново пишет только производные отчёты. При ошибке анализа прежние отчёты не изменяются. Сбой записи производных отчётов может оставить их частично обновлёнными; функция бросит исключение, а исправный журнал останется источником пересчёта.

## Файлы запуска

| Файл | Содержание |
|---|---|
| manifest.json | Версия формата, incomplete/complete, вариант, параметры, tick_ns, сведения о программе/компиляторе/платформе, численные правила и контрольные суммы |
| input/scenario.json, input/delivery.csv | Точные копии исходных байтов, без преобразования чисел |
| events.jsonl | Канонический поток всех событий, диагностика и отметка успешного завершения |
| tasks.csv | Исходные ID/поступление/работа, принятое завершение, latency, число назначений и незавершённость |
| attempts.csv | Ключ task_id/attempt_no, узел, назначение, физическое начало/завершение/прерывание, отзыв, принятие и решение по результату |
| nodes.csv | Crash, FAILED, итоговая оценка, классификация, зафиксированный набор возврата, Detection/Recovery и причины отсутствия |
| metrics.json | Метрики запуска, числа наблюдений, единицы, окна throughput и проверенные инварианты |

Manifest сначала имеет status=incomplete. Только после успешной записи всех файлов он становится complete. Ошибка моделирования, анализа или записи не выдаётся за успешное достижение горизонта; неполный/повреждённый manifest или журнал отклоняется пересчётом. Незавершённые задачи при корректном учёте разрешены и не мешают status=complete.

Контрольная сумма — стабильный FNV-1a-64 по байтам файла, 16 шестнадцатеричных цифр. Это проверка целостности для воспроизведения, не криптографическая защита от намеренной подмены. Суммы исходных JSON/CSV и журнала указаны с названием алгоритма. Manifest хранит исходные абсолютные пути как происхождение, но пересчёт использует относительные input/*; исходные файлы больше не нужны. Для этого добавлена явная перегрузка load_scenario(json, delivery_override): путь CSV в JSON по-прежнему валидируется, фактический CSV берётся из снимка. JSON не переписывается и не пропускается через double.

## Формат events.jsonl версии 1

Каждая строка — JSON-объект с schema_version=1, record_no начиная с 1, time_ticks, phase и kind. В начале run_started с временем/фазой 0; в конце run_completed с фазой 0, достигнутым горизонтом и executed_events. Фаза 0 — только служебная граница файла, не фаза движка.

Событие движка имеет фазу 1–8, tie_key из четырёх uint64 и action_sequence — insertion_sequence движка. Несколько строк одного действия сохраняют один ключ; record_no различает их порядок. Времена, ID, поколения и счётчики — непосредственно JSON integers. Дробные/экспоненциальные тики и bool вместо числа запрещены.

| kind | Восстановимые данные |
|---|---|
| task_arrived, task_assigned, physical_assigned | Описание исходной задачи и команда назначения |
| physical_started, physical_finished, crash | Физические времена, длительность, срок, отдельный токен и прерванная попытка |
| result | Принятое/отклонённое сообщение с решением |
| reconfiguration | Полный ALIVE, новые FAILED и общий сортированный список отозванных попыток |
| heartbeat_sent, heartbeat_delivered, send_skipped | Номер, задержка/отправка, планируемый приём, потеря/blackout/горизонт или остановка после crash |
| heartbeat_observed | Допустимость, до/после, контакт, поколение, новые таймеры и статистика/пороги |
| timeout_observed, completion_skipped | Запрос/поколение, решение, до/после и пороги либо физические токены/причина пропуска |
| dispatch | Размер единственной пачки распределения отметки |

Кодек также умеет представить assignment_revoked; интегрированный запуск использует совместный reconfiguration, поэтому отдельный отзыв не принимается интегрированным Analyzer. Весь набор отзывов восстанавливается из reconfiguration.

Вещественные работа, исходные пороги и статистика журнала представлены строками *_decimal в classic locale с max_digits10 для long double. Это сохраняет их при чтении без промежуточного double и не ограничивает диапазон double на других платформах. Представимые пороги — целые тики; читатель повторно проверяет их соответствие raw-порогам. В metrics.json средние и throughput — отображаемые JSON numbers с точностью double; целые длительности/времена/счётчики сохраняют точность. CSV вещественных значений использует max_digits10 и classic locale.

Журнал не содержит системного времени, выходного пути или случайных значений. В одной сборке повтор и перестановка четырёх вариантов дают идентичные events.jsonl, metrics.json и CSV. Побитовая идентичность вещественных расчётов разных компиляторов не обещается.

Читатель отклоняет неизвестные поля/виды/enum, дубликаты JSON-ключей, недопустимые числа, пропуски record_no, отсутствие/повтор окончания и строки после него. Ошибка содержит номер строки. Analyzer дополнительно проверяет порядок ключей, фазы, исходные ID/описания, FIFO назначений и физической очереди, текущую попытку, одно принятие, физическую длительность, общую сортировку возврата, пакетность и итоговые множества/баланс. Это пересчёт по журналу с проверкой согласованности; он не повторяет выбор RR/LL или статистический алгоритм детектора. Контрольные суммы обнаруживают изменение сохранённого потока между записью и пересчётом.

Память Writer — одна запись; Reader — одна строка. Analyzer хранит задачи, попытки, состояния, FIFO и завершённые latency для P95; полный поток heartbeat/таймеров не накапливается. Число попыток влияет на память итогового отчёта. Все вспомогательные события сохраняются; переключатель детализации пока не добавлен.

## Метрики и отсутствующие значения

Detection — FAILED минус настоящий crash. FAILED до crash остаётся FP; последующий crash получает crash_after_false_exclusion без нового Detection и без FN. Crash без FAILED на горизонте — FN и not_detected. Для корректного FAILED набор R фиксируется один раз по реальным отзывам этой реконфигурации; назначения после crash до обнаружения включаются. Повторные переназначения не меняют R. Recovery — последнее окончательное принятое завершение R минус crash; пустой R даёт Detection, незавершённый член R — null/recovery_incomplete.

Latency считается только по уникальным принятым задачам относительно исходного поступления. P95: сортировка и ближайший ранг n-n/20, без умножения/переполнения. Средние рассчитываются в long double без суммирования огромных целочисленных времён. Throughput учитывает только (start,end] и вычисляется как count*1e6/duration_ticks, в задачах/с; это та же формула через секунды с одним делением. Пустое окно даёт 0.

Счётчик retries увеличивается на каждое назначение после первого, отдельно считается rejected_revoked_results. Баланс: arrived=completed+unfinished и unfinished=queued+assigned, проверяются множества, уникальность и соответствие физических попыток. Отсутствующие времена — optional; JSON null с причиной, CSV пустое численное поле с отдельной причиной. Причины: not_detected, recovery_incomplete, crash_after_false_exclusion; пустое среднее/P95 — empty_sample; для узла без применимого настоящего отказа — not_applicable. В tasks.csv незавершённая latency имеет причину unfinished.

Средние Detection/Recovery внутри запуска выводятся с detection_samples/recovery_samples, latency — с latency_samples. FP/FN, поздние crash и незавершённые Recovery сохраняются отдельно. Агрегация серии запусков, comparison.csv/summary.csv и команды CLI относятся к следующему этапу.
