# Контракт модели экспериментального стенда НИР

Версия контракта: 1. Правила зафиксированы на этапе 0. Текущее состояние: этап 3 — логические задачи, попытки, время, базовые типы и сборка; распределители, детекторы и симулятор ещё не реализованы.

Основание: [план реализации](../План_реализации_НИР_Codex.md), разделы 3–10 и 12. План прочитан целиком. Контракт фиксирует его семантику для последующей реализации; он не подтверждает работоспособность ещё не написанного стенда. При содержательном противоречии с планом требуется явно разобрать противоречие, а не менять алгоритм молча. `НИР_черновик.docx` не редактируется. Для этапа 0 достаточно правил, явно изложенных в плане; сверка с содержимым DOCX не заявляется.

## 1. Объём и происхождение решений

Стенд — однопоточная дискретно-событийная консольная программа на C++20. Время перескакивает к очередному событию. Нет реальных потоков, ожиданий, сети, датчиков, БД, брокеров и кластера. Сравниваются `fixed_rr`, `fixed_ll`, `adaptive_rr`, `adaptive_ll` на одних сохранённых входах.

| Уже задано планом, не выбирается в сценарии | Задаётся входными данными |
|---|---|
| Граница ядра, движка и физической среды; отсутствие скрытого знания в ядре | Состав узлов и их постоянные производительности |
| Восемь фаз, правила равенства и включённый горизонт | Горизонт, исходные задачи, crash, перерывы доставки |
| Одна микросекунда на тик; `tick_ns = 1000` | Целые временные значения в этой единице |
| FIFO, одна физическая попытка за раз, полная работа при повторе | Положительные работа задач и производительность узлов |
| Формулы Load, порогов, метрик и окончательность FAILED | `H`, `tau0`, `kappa`, `M`, `m_min`, `c` в допустимых диапазонах |
| Допустимость heartbeat, поколения, однократный отзыв | Полная таблица потенциальных доставок, окна throughput |
| Четыре сочетания используют одинаковые входы | Выбор одного сочетания для `run`; список повторов для `batch` |

Границы модулей, целочисленный тик и округление — дополнения реализации для главы 3, уже согласованные в плане. Технические решения этого контракта: положительные ID на основе `std::uint64_t`, счётчики с контролем переполнения, `long double` для вычислений работы/нагрузки/статистики и допуск аудита сумм из раздела 4. Эти решения не изменяют формулы модели. Их проверка кодом относится к последующим этапам.

Демонстрационные числа и ручные примеры служат проверками. Они ещё не являются результатами исследования и не доказывают преимущества алгоритма.

## 2. Сущности и владение состоянием

| Сущность | Данные и инварианты | Владелец |
|---|---|---|
| Описание узла | Положительный уникальный ID, конечная `p > 0` в единицах работы/с, неизменны в запуске | Неизменяемый сценарий |
| Описание задачи | Положительный уникальный ID, исходные `arrival_ticks` и конечная `w > 0`; не меняются при повторе | Неизменяемый сценарий |
| Логическая задача | Ещё не поступила; либо в общей очереди; либо имеет одно актуальное назначение; либо завершена единственным принятым результатом | Ядро |
| Попытка | Ключ `(task_id, attempt_no)`, номер от 1; узел, время назначения, отзыв, принятие результата; история сохраняется | Ядро |
| Физическая попытка | Копия выданной работы, локальная очередь, начало/завершение, отдельный токен актуальности завершения | Среда |
| Оценка узла | ALIVE, SUSPECT, FAILED; история контактов, последние номер и время, пороги, поколение; признак выполненной реконфигурации | Ядро |
| Фактический узел | Работоспособность, одна выполняемая попытка, FIFO ожидающих физических попыток, отправки heartbeat | Среда |
| Событие | Время, численная фаза, стабильный ключ равенства, последовательность вставки, действие | Движок |
| Метрики | Вычисляются из журнала и исходного сценария, включая скрытое от ядра фактическое состояние | Внешний модуль метрик |

Отсутствующие времена представлены `optional`, в файлах — `null` либо пустым полем с причиной по схеме. Ни ноль, ни `-1` не обозначают отсутствие. Нулевое модельное время действительно допустимо.

В начале все узлы физически исправны и имеют оценку ALIVE; очереди пусты. Начальный контакт детектора равен 0, последний номер heartbeat — 0, статистическая история пуста. Начальный искусственный контакт не является реальным heartbeat.

Для уже поступивших задач всегда выполняется `N_in = N_done + N_unfinished`. Каждая незавершённая задача ровно один раз находится в общей очереди либо имеет одно актуальное назначение; завершённая отсутствует в обоих множествах. Ещё не поступившие задачи не входят в `N_in`. Старые физические попытки не увеличивают число задач.

## 3. Архитектурные границы и API

Планируемый граф зависимостей: `core → common`, `engine → common`, `simulation → core + engine + common`. CLI, IO и метрики находятся снаружи. Ядро и движок не зависят друг от друга; ядро можно проверять без симулятора и файлов.

Ядро владеет общей FIFO, назначениями, номерами попыток, нагрузкой, детектором, позицией RR и однократностью реконфигурации. Оно принимает наблюдения с явным `SimTime` и возвращает типизированные решения:

| Операция | Вход | Эффект / выход |
|---|---|---|
| Поступление | Время, задача | Добавить в общую очередь |
| Heartbeat | Время, узел, номер | Принять/отклонить; обновить контакт, пороги, поколение; вернуть запросы проверок |
| Тайм-аут | Время, узел, поколение, вид | Проверить актуальность; изменить оценку или пропустить |
| Результат | Время, задача, попытка, узел | Атомарно принять и обновить состояние либо отклонить |
| Применение доступности | Время, накопленные изменения | Совместно обновить ALIVE и отозвать назначения новых FAILED |
| Dispatch | Время | Последовательность команд назначения |

Запрос таймера: абсолютный срок, узел, поколение, вид SUSPECT/FAILED. Команда назначения: задача, узел, номер попытки. Аудит ядра — структурированные записи через небольшой наблюдатель или возвращаемый список.

Ядро не включает заголовки движка, не владеет очередью событий, не читает файлы, не использует RNG, не знает crash, будущие доставки, фактические очереди и остаточную работу. Адаптер переводит только разрешённые наблюдения, исполняет назначения и ставит таймеры. Отчёт по попытке объединяет логические и физические записи по `(task_id, attempt_no)` снаружи ядра.

Движок знает только универсальный ключ и действие, проверяет допустимость планирования и останавливается при ошибке. Смысл heartbeat, ALIVE, Load и телеметрии в нём отсутствует.

## 4. Время, числа и допуски — дополнения главы 3

Один тик = 1 мкс, `ticks_per_second = 1 000 000`, `tick_ns = 1000`. Другой `tick_ns` отклоняется. Отметки `SimTime` и интервалы `SimDuration` — разные небольшие типы на основе `std::int64_t`; допустимый диапазон каждого неотрицателен и не превышает `INT64_MAX`. Все временные входы имеют `_ticks` и разбираются непосредственно как целые, без промежуточного `double`. Дробное значение, даже `1.0`, не соответствует целочисленному формату временного поля.

ID узлов, задач, сообщений, номера попыток положительны; 0 для последнего принятого номера — только начальное внутреннее состояние. Счётчики поколения, вставок и записей могут начинаться с 0. Увеличение любого счётчика проверяется до операции, переполнение является ошибкой.

Обработка полной работы:

```text
processing_ticks = max(1, ceil((w / p) * 1 000 000))
```

Математические пороги сначала вычисляются в тиках без округления, затем преобразуются:

```text
suspect_ticks = ceil(raw_suspect_ticks)
failed_ticks  = max(suspect_ticks + 1, ceil(raw_failed_ticks))
```

Второй математический порог умножает исходный первый порог, а не округлённый. Минимум один тик между представимыми порогами сохраняет отдельную стадию SUSPECT. Журнал содержит математические и округлённые пороги.

Работа, производительность, нагрузки, среднее и дисперсия вычисляются в `long double`; формат IO обязан сохранять достаточную точность для повторного чтения. Все входные и промежуточные вещественные значения проверяются на конечность, диапазон и допустимость. В частности, слишком малая положительная работа не должна после вычисления превращаться в мгновенную обработку; недопустимую потерю представимости следует выявлять. До преобразования `ceil` в целое проверяется диапазон, до сложения — переполнение. Ошибка численного представления не заменяется насыщением или значением по умолчанию.

Срок за горизонтом можно не ставить: сначала сравнить длительность с `horizon - now`, не вычисляя потенциально переполняющееся `now + duration`. Нельзя молча отбрасывать событие в пределах горизонта. Положительная обработка длится не меньше тика.

Временные отметки сравниваются точно. В выборе LL нет epsilon: разные представимые нагрузки остаются разными. Только для проверки накопленной суммы `W` против независимого пересчёта разрешается:

```text
abs(W_counter - W_recomputed) <= tolerance
tolerance = 64 * epsilon(long double) * max(1, n) * max(1, sum_abs_work)
```

Здесь `n` — число слагаемых актуальных назначений узла, `sum_abs_work` — сумма их абсолютных исходных работ. Сам расчёт допуска также проверяется на конечность. При пустом наборе требуется точный ноль, независимо от допуска. Это технический допуск проверки вещественного суммирования, а не алгоритм выбора или исправления нагрузки. Малые ручные целые примеры проверяются точно, если вычисления представимы точно; проверки иных вещественных расчётов явно задают обоснованный допуск и не сравнивают им времена.

Секунды используются только для вывода и метрик в задачах/с. Системные часы не управляют моделью и не попадают в канонический журнал. Достаточность микросекундной сетки проверяется перед исследовательскими сериями. Изменение разрешения требует общего контракта и версии формата для всех вариантов.

## 5. Задачи, распределение и результаты

Общая и локальные очереди FIFO, вместимость не ограничена моделью. Физический узел исполняет одну попытку без вытеснения. Освободившийся исправный узел немедленно начинает следующую старую локальную попытку, включая состояния SUSPECT и ложный FAILED.

Dispatch назначает, пока общая очередь непуста и существует ALIVE. Занятость не запрещает выдачу: задача попадает в локальную очередь. До детектирования crash назначения ещё считающемуся ALIVE остановленному узлу продолжаются. SUSPECT прекращает только новые назначения, сохраняя работу. FAILED окончателен до конца запуска; рестарта нет.

Назначение удаляет задачу из общей очереди, создаёт следующую попытку и сразу увеличивает нагрузку. Первая попытка — 1, каждая повторная использует тот же ID задачи, исходное поступление и полную исходную работу.

### Round Robin

Исходные ID и доступные ALIVE упорядочены по возрастанию. Первое назначение — минимальному ID. После выдачи сохраняется следующий доступный ID по кругу. При совместном изменении доступности:

1. Сохранить ID предполагаемого следующего исполнителя.
2. Если он доступен, оставить позицию на нём, в том числе при возврате других узлов из SUSPECT.
3. Если исчез — взять первый доступный после него по циклическому порядку исходных ID.
4. Если доступных нет — сохранить ориентир до их появления и затем применить то же правило.

Позиция корректируется один раз после всех изменений отметки. Выбор по подготовленной позиции — O(1); перестроение списка учитывается отдельно.

### Least Loaded

```text
W_i    = сумма исходных w всех актуальных неотозванных незавершённых назначений i
Load_i = W_i / p_i
```

Полная работа текущей попытки входит в `W_i`; течение времени её не уменьшает. Load не является длиной очереди или точным остаточным временем. Выбирается минимум среди ALIVE, при точном равенстве — меньший ID. Счётчик обновляется после каждой команды, поэтому следующие назначения той же отметки видят новую нагрузку. Принятие либо отзыв снимают работу ровно один раз; пустой набор назначений и реконфигурация дают точный ноль. Получение Load — O(1), выбор узла — линейный.

### Приём результата

Принимается только точное совпадение `(task_id, attempt_no, node_id)` с актуальным неотозванным назначением ещё незавершённой задачи. Проверка, завершение задачи, удаление назначения и снятие нагрузки — одно логическое действие. Физическое состояние узла не входит в проверку ядра. Старые и повторные результаты лишь журналируются как отклонённые, не меняя счётчики и новую нагрузку. После отзыва отсутствие нового назначения также не позволяет принять старый результат.

## 6. Heartbeat, канал и детектор

Heartbeat отправляется в `H, 2H, 3H, …`, `H > 0`; номера от 1 растут при отправке. Занятость не влияет на отправки. Crash прекращает будущие отправки, но уже отправленное остаётся в канале. Ложный FAILED физически исправного узла отправки не прекращает.

Трасса задаёт `(node_id, heartbeat_seq) → (delay_ticks, lost)`, где задержка целая неотрицательная, `lost` строго 0/1. Потеря не порождает получение и повторную отправку. Перерыв `[start, end)` отбрасывает сообщение, если его планируемое получение попадает в этот полуинтервал, даже при отправке до начала перерыва. На `start` сообщение теряется, на `end` проходит; доставки после перерыва взамен потери нет. Пересечения перерывов трактуются как объединение: принадлежность хотя бы одному достаточна для потери.

Допустим только номер строго больше последнего принятого, если узел ещё не FAILED. Недопустимое сообщение не меняет контакт, историю, пороги и поколение. Отправленный до crash heartbeat после crash обрабатывается по обычным правилам: скрытая работоспособность не проверяется. После FAILED все heartbeat игнорируются детектором.

Первый допустимый heartbeat создаёт первый реальный контакт, но не интервал от искусственного нуля. Только со второго допустимого сообщения добавляется разность времён допустимых получений. Одинаковые времена дают допустимый нулевой интервал.

### Пороги и переходы

Общие ограничения: `tau0_ticks >= H_ticks > 0`, конечная `kappa > 1`; `M >= m_min >= 2` — целые, конечная `c >= 0`.

| Политика | Математический первый порог | Математический второй порог |
|---|---|---|
| Fixed | `tau0_ticks` | `kappa * tau0_ticks` |
| Adaptive до прогрева | `tau0_ticks` | `kappa * tau0_ticks` |
| Adaptive после прогрева | `max(H_ticks, mean + c * sample_std)` | `kappa * raw_suspect_ticks` |

Окно содержит последние не более `M` интервалов. Среднее арифметическое; выборочная дисперсия делится на `m - 1`. Для прогрева нужны `m_min` интервалов, то есть минимум `m_min + 1` допустимых сообщений. Нулевые интервалы и большие интервалы из-за потерь не фильтруются. При переполнении окна удаляется самый старый интервал. Допустим устойчивый двухпроходный расчёт O(M). Пороги пересчитываются только после допустимого heartbeat; в отсутствие сообщений заморожены.

Оба срока отсчитываются от последнего допустимого контакта, а не от перехода в SUSPECT. При инициализации создаются оба срока от 0. Каждый допустимый heartbeat увеличивает поколение и возвращает новые запросы сроков. Старое поколение недействительно даже при совпадении нового времени контакта со старым. Удалять старые события из очереди необязательно; их пропуск диагностируется.

Действующая проверка сначала сравнивает `elapsed >= failed_ticks`, затем `elapsed >= suspect_ticks`. Иначе оценка не меняется. Допустимый heartbeat до FAILED устанавливает ALIVE, позволяя SUSPECT → ALIVE. FAILED терминален. Вид таймера стабилизирует порядок, но не заменяет проверку фактически достигнутых порогов.

## 7. Crash и совместная реконфигурация

На узел допускается не более одного crash, включая время 0. Среда останавливает исполнение и heartbeat, инвалидирует завершение прерванной физической попытки отдельным токеном среды. Ядро не получает уведомления о crash. Токен завершения, поколение детектора и номер попытки — три разных механизма.

Для всех новых FAILED одной отметки в фазе 6 ровно один раз:

1. Исключить их из новых назначений.
2. Собрать все актуальные незавершённые назначения, в том числе выданные после физического crash.
3. Отозвать старые попытки, удалить актуальные назначения, снять их нагрузку.
4. Объединить задачи без дубликатов, отсортировать по `(original_arrival_ticks, task_id)`.
5. Добавить общий набор в конец существующей FIFO, сохранив прежний порядок её содержимого.
6. Зафиксировать отдельный набор возврата для каждого нового FAILED для метрик; распределять только в фазе 8.

Повторная обработка того же FAILED не возвращает задачи заново. Изменения ALIVE/SUSPECT также требуют совместного обновления списка распределения, даже без нового FAILED.

Логический отзыв не отменяет физическую попытку или локальную очередь исправного ложно исключённого узла. Он продолжает старую работу и выдаёт отклоняемые результаты. Только последующий физический crash останавливает эту работу.

## 8. Порядок событий и горизонт

Очередь движка — минимум по `(time_ticks, phase, tie_key, insertion_sequence)`. Ключи задаёт адаптер, не адреса объектов и не порядок обхода `unordered_map`.

| Фаза | Действие | Стабильный порядок внутри фазы |
|---|---|---|
| 1 | Физический crash и инвалидирование завершения | ID узла |
| 2 | Физические завершения, немедленный результат ядру, старт следующей старой локальной попытки | ID узла, затем `(task_id, attempt_no)` |
| 3 | Отправки heartbeat исправными узлами | ID узла, затем номер heartbeat |
| 4 | Получения heartbeat, фильтрация и обновление детектора | ID узла, затем номер heartbeat |
| 5 | Актуальные таймеры, изменения оценок | ID узла, затем вид (SUSPECT перед FAILED), затем поколение |
| 6 | Одно совместное применение доступности и реконфигурация | Одна обработка на отметку; узлы по ID |
| 7 | Новые поступления | ID задачи |
| 8 | Один dispatch, синхронный старт свободных исправных узлов | FIFO задач и выбранная стратегия |

При полном равенстве ключей действует последовательность вставки. Адаптер объединяет запросы фаз 6 и 8: не более одной обработки каждого вида на отметку. Все поступления отметки предшествуют выдаче. Промежуточные изменения доступности не двигают RR несколько раз.

Во время исполнения запрещена вставка в прошлое, в пройденную или текущую фазу текущей отметки. Мгновенные последствия исполняются синхронно или ставятся в последующую фазу. Нулевая задержка из фазы 3 создаёт приём в фазе 4 той же отметки. Положительная обработка никогда не создаёт завершение в уже пройденной фазе 2.

Следствия: crash одновременно с завершением подавляет результат; допустимый результат одновременно с будущим FAILED принимается до реконфигурации; heartbeat на сроке таймера обрабатывается раньше таймера и инвалидирует старое поколение.

Все фазы `time <= horizon_ticks` выполняются, позднейшие события — нет. Горизонт положителен. Отсутствие ALIVE и незавершённость допустимы. Технический лимит событий, исключение, ошибка записи или численная ошибка означают неполный/ошибочный запуск с ненулевым выходом, а не успешное достижение горизонта.

## 9. Входы и воспроизводимость

Материализованный сценарий: `scenario.json` и `delivery.csv`, путь трассы относительно JSON. Поля JSON: `schema_version`, `tick_ns`, `horizon_ticks`, `heartbeat_period_ticks`, `tau0_ticks`, `kappa`, `adaptive.{window,min_intervals,c}`, `nodes[]`, `tasks[]`, `crashes[]`, `blackouts[]`, `measurement_windows[]`, `delivery_trace`. Первой версии формата соответствует `schema_version = 1`.

Узел содержит `id, performance_work_per_second`; задача — `id, arrival_ticks, work`; crash — `node_id, at_ticks`; перерыв — `node_id, start_ticks, end_ticks`; окно — `start_ticks, end_ticks`.

CSV имеет заголовок `node_id,heartbeat_seq,delay_ticks,lost` и ровно одну запись каждого потенциального heartbeat каждого исходного узла с номерами `1..floor(horizon/H)`, включая неиспользуемые отправки после crash. При `horizon < H` требуемых записей нет. Доставки за горизонтом могут оставаться неисполненными.

Валидация отклоняет неверные типы, дробные тики, отрицательные времена, NaN/inf, недопустимые настройки и переполнения; повторяющиеся ID, crash одного узла и ключи трассы; неизвестные ссылки; неполную трассу. Для задач и crash: `0 <= time <= horizon`; для перерывов — корректные неотрицательные полуинтервалы `start < end`; для окон throughput — `0 <= start < end <= horizon`. Ошибка содержит файл и поле/строку. Некорректный вход не исправляется молча. Пустой поток задач допустим.

После загрузки исходные данные неизменяемы, каждый вариант получает собственное состояние. `run` и `compare` не используют случайность. Порядок запуска вариантов не влияет на отдельные результаты.

Генератор до моделирования сохраняет полный сценарий, настройки, seed, версию и среду. Поддерживает периодические поступления, постоянную либо ограниченную конечным диапазоном работу, равномерные целые задержки и вероятность потерь `q ∈ [0,1]`, явные crash и перерывы. Обход узлов и сообщений стабилен; допускается `std::mt19937_64`. Seed сам по себе не обещает одинаковые стандартные распределения в разных стандартных библиотеках. Основание сравнения — сохранённые входы. Каждый повтор серии имеет отдельные сохранённые входы, общие для его четырёх вариантов.

Один вариант на тех же входах в одной сборке даёт одинаковые канонические журнал и метрики. Межплатформенная побитовая идентичность вещественных расчётов не обещается. Manifest хранит версии программы, компилятора, платформы, зависимостей, численные правила и стабильные контрольные суммы входов.

## 10. Журнал и точные определения метрик

`events.jsonl` записывается последовательно без удержания большого журнала в памяти. Общие поля: последовательный номер, целое модельное время, фаза, вид. Дополнительные: узел, задача, попытка, номер heartbeat, поколение, прежняя/новая оценка, решение, причина и пороги по смыслу события.

Журнал позволяет восстановить поступление, назначение, физические начало/завершение, принятие/отклонение результата, crash, приём/отклонение heartbeat, пороги, переходы оценок, отзыв и набор возврата. Потери и устаревшие таймеры доступны для диагностики; уровень вспомогательной детализации не исключает записи для основных метрик. Системное время запуска в канонический журнал не входит.

| Показатель | Единственное определение |
|---|---|
| Detection Time | `t_det - t_fail` только для корректного FAILED после физического crash; SUSPECT не считается обнаружением |
| FP | Число FAILED при ещё физически работающем узле; последующий crash не меняет классификацию |
| FN | Число физически отказавших узлов с оценкой не FAILED на горизонте |
| Crash после ложного исключения | Отдельный счётчик; не FN и не корректное обнаружение; нового Detection Time нет |
| Recovery Time | Для набора `R_i`, однократно зафиксированного при корректной реконфигурации: `max(final_accepted_time_j, j ∈ R_i) - t_fail`; для пустого набора — Detection Time |
| Throughput | Уникальные принятые завершения в `(t1,t2]`, делённые на `(t2-t1)/1 000 000` секунд; без завершений — 0 |
| Latency | Принятое завершение минус исходное поступление для каждой уникальной завершённой задачи; среднее и P95 |
| P95 | Ближайший ранг `ceil(0.95*n)` с нумерацией от 1; безопасная целочисленная формула `n - floor(n/20)` для `n > 0` |
| Повторные назначения | Каждое назначение начиная со второго: три назначения дают два повтора; отдельно число отклонённых результатов отозванных попыток |
| Сохранность | Баланс и множества задач из раздела 2; старые физические попытки не входят как отдельные задачи |

Набор `R_i` включает назначения после crash до детектирования. Последующие переназначения не меняют членство задачи. Recovery использует окончательные принятые завершения, а не конец старой физической попытки или восстановление throughput. Если хотя бы один член набора не завершён к горизонту — Recovery отсутствует.

Отсутствующие значения: `null` с причиной `not_detected`, `recovery_incomplete`, `crash_after_false_exclusion` или `empty_sample` по контексту. Для CSV — пустое численное поле и отдельная причина. Нельзя подставлять 0, бесконечность или горизонт. Пустая выборка latency/P95 отсутствует; throughput пустого потока равен 0, моделирование heartbeat и отказов продолжается.

Сначала рассчитываются метрики запуска. В серии усредняются только определённые значения с явным числом наблюдений. Средняя latency и P95 сначала вычисляются по каждому запуску, затем усредняются отдельно. Для Detection/Recovery отдельно показываются числа определённых наблюдений внутри запуска и число запусков: усреднение по отказам нельзя молча смешивать с усреднением по запускам. FP/FN, незавершённые восстановления и прежние ложные исключения сохраняются отдельно.

Метрики пересчитываются отдельным модулем из исходных данных и сохранённого журнала. Скрытые сведения доступны этому анализу, но не возвращаются алгоритмам. Нарушение баланса/уникальности делает запуск ошибочным и исключает его из научного сравнения.

## 11. Выходы, CLI и ограничения сборки

Запуск создаёт `manifest.json`, `events.jsonl`, `tasks.csv`, `attempts.csv`, `nodes.csv`, `metrics.json`. CSV задач содержит исходное поступление, принятое завершение, latency, число попыток и незавершённость; CSV попыток связывает назначения, физические времена, отзыв и решение; CSV узлов содержит crash, FAILED, классификацию, Detection/Recovery и причины отсутствия. Везде, где нужны единицы, они заданы явно; вывод детерминированно упорядочен.

`compare` создаёт `fixed_rr`, `fixed_ll`, `adaptive_rr`, `adaptive_ll` и `comparison.csv`. `batch` читает сохранённый список сценариев с ID сценария и повтора, не генерирует сеть внутри сравнения, добавляет `summary.csv` с размерами выборок.

Планируемый CLI: `telemetry_sim validate`, `generate`, `run`, `compare`, `batch`, `metrics`, `--help`. Неизвестные параметры и ошибки дают понятную диагностику и ненулевой выход. Непустой каталог результатов не затирается без `--overwrite`. Ошибки записи и неполные результаты отличимы от успеха.

C++20 без расширений (`CXX_EXTENSIONS OFF`), CMake не ниже 3.20, предупреждения для собственного кода, CTest. На этапе 1 закреплён `nlohmann/json` 3.12.0 с SHA-256 релизного архива; установленный пакет принимается только этой версии. Собственный JSON-парсер запрещён. Проверки работают и в Release, не основаны только на `assert`. Debug/Release и доступные ASan/UBSan проверяются фактически; непроверенные платформы не объявляются проверенными. Сборка, зависимости и большие сгенерированные результаты отделены от исходников. Ограничения путей с двоеточием и команды сборки описаны в [README](../README.md).
