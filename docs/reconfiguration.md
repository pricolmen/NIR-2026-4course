# Совместная реконфигурация

Этап 6 реализован в [Dispatcher](../include/telemetry/core/dispatcher.hpp), [координаторе](../src/core/dispatcher.cpp) и [подготовке отзыва TaskStore](../src/core/task_store.cpp). Основание — раздел 6.6 исходного плана и [контракт](model_contract.md).

## Одна операция доступности

```cpp
auto report = dispatcher.apply_availability(at, final_alive, failed_notifications);
// Затем поступления этой отметки; dispatch вызывается отдельно после них.
```

`final_alive` содержит весь итоговый ALIVE-набор, `failed_notifications` — все уведомления FAILED данной отметки. Входные ID сортируются; неизвестные и повторные ID отклоняются. FAILED сохраняется в отдельном неизменяемом снаружи отсортированном наборе. Повторное уведомление уже исключённого узла допустимо: новых отзывов нет. Узел FAILED нельзя включить в ALIVE ни этим методом, ни `set_alive`. Одновременное включение одного ID в ALIVE и FAILED — ошибка.

Новые FAILED определяются разностью входного и сохранённого множеств. Из реестра собираются только актуальные незавершённые назначения этих узлов. Каждая задача встречается один раз по построению реестра. Общий набор сортируется по исходному времени поступления, затем ID, независимо от порядка узлов и времени последнего переназначения. Он добавляется в конец уже существующей FIFO; прежняя часть очереди не сортируется. Старые попытки получают `revoked_at`, текущий номер снимается. Записи завершённых задач и старых отозванных попыток сохраняются.

Все текущие назначения новых FAILED отзываются, поэтому их счётчики работы, компенсации и числа назначений получают точный ноль одним действием. Последовательного вычитания работ внутри пачки нет. Нагрузка других узлов не меняется. Один итоговый ALIVE-набор один раз подготавливает новую позицию RR. Для LL дальнейшие назначения видят уже обновлённую нагрузку после каждой команды.

Возвращается `ReconfigurationEvent{at, alive, newly_failed, revoked}`: канонический итоговый ALIVE, только новые FAILED и прежние тройки `(task, attempt, node)` в порядке возврата. Тот же payload передаётся наблюдателю единственным событием. Отдельные `AssignmentRevokedEvent` на каждую задачу пачки не посылаются, поэтому поток событий не дублирует отзывы. Время/исходная работа доступны через неизменное описание задачи в реестре.

`set_alive(at, ids)` сохранён как обёртка без новых FAILED. Он подходит для SUSPECT и возврата SUSPECT → ALIVE: старые назначения и нагрузка сохраняются. Теперь эта операция также журналирует итоговое изменение доступности. Отсутствие узла в ALIVE само по себе не означает FAILED.

## Целостность и результат

До изменения состояния готовятся новые множества, копии RR/нагрузки, сортированный набор отзывов, будущая FIFO и payload журнала. TaskStore предоставляет эти подготовку/применение только Dispatcher через private-доступ, а не внешний изменяемый план. Указатели плана действуют только между подготовкой и немедленным применением без промежуточных операций. Применение TaskStore и обмены подготовленными состояниями не выделяют память и не вызывают callback. После них наблюдатель видит всю пачку: очередь, историю, ALIVE, FAILED, RR и нагрузку согласованы.

Неверный вход или ошибка подготовки сохраняет состояние и время последнего наблюдения. Исключение внешнего наблюдателя возникает после целостного логического обновления, не откатывает его и означает ошибочный запуск. Продолжать моделирование после ошибки журнала нельзя. Повторный вход из callback запрещён. Повторные уведомления FAILED не создают повторного возврата даже после такой ошибки; это дополнительно проверено на уровне состояния.

Принятие результата остаётся общей операцией TaskStore/Dispatcher с единым `inspect_result`. Старая попытка после отзыва получает `no_current_assignment`, после нового назначения — `attempt_mismatch`, после завершения — `already_completed`. Даже при повторном назначении тому же узлу номер попытки различается. Отклонение не снимает работу нового назначения. Новое назначение использует полную исходную работу, исходное поступление и следующий номер попытки; физический прогресс не учитывается.

## Логический отзыв и физическая среда

Операция возвращает сведения о логических отзывах и не создаёт команд физической отмены, очистки очереди или остановки исполнителя. Она не получает данные о физической работоспособности и не обращается к среде. Физически исправный узел с ложным FAILED продолжит текущую и старую локальную работу по правилам этапа 8; её прежние результаты уже сейчас отклоняются ядром даже без переназначения. На этапе 8 [физическая среда](physical_environment.md) отменяет завершения после crash через отдельный токен. Поколения детектора и номера попыток эту роль не выполняют.

Проверки этапа 6 сохраняют выданные команды во внешнем тестовом векторе и передают старые результаты после реконфигурации. Это проверка границы API и защиты результатов, а не реализация физических очередей/времени исполнения. Ручная связка с Detector подтверждает SUSPECT без отзыва и отзыв при FAILED. Назначение до обнаружения условного crash также попадает в возврат; сам скрытый crash ядру не передаётся.

## Сложность и последующая интеграция

Пусть N — каталог узлов, A — итоговый ALIVE, B — входной FAILED-набор, F — уже исключённые узлы, T — число поступивших задач, K — число возвращаемых задач, Q — размер прежней FIFO. Подготовка множеств требует сортировок O(A log A + B log B) и проходов по F/B, проверок принадлежности и подготовки RR. Копии RR/нагрузки дают O(N) дополнительной памяти и O(N) ожидаемого времени. Поиск нагрузок использует hash-таблицу только для адресации, порядок решений задаётся отсортированными векторами.

При новых FAILED реестр сканируется за O(T log(B+1)); сортировка возврата — O(K log K). При K > 0 копия FIFO добавляет O(Q + K) памяти/времени. При отсутствии новых FAILED реестр не сканируется; при K = 0 FIFO не копируется и сохраняется. Подготовка обеспечивает целостное применение ценой временных копий; ускорение без измеренной необходимости не вводилось. Сложность отдельных стратегий RR/LL не меняется; применение доступности Dispatcher теперь включает описанные затраты.

Вызывающий адаптер обязан собрать все изменения одной отметки перед одним вызовом, затем подать поступления и выполнить один dispatch в фазе 8. Прямой API не определяет фазы и допускает несколько операций одного времени, в том числе проверку идемпотентности. Очередь событий и автоматическое объединение будут реализованы на этапах 7–10. Пять групп [reconfiguration_tests.cpp](../tests/reconfiguration_tests.cpp) и результаты трёх сборок описаны в [самоаудите](stage_6_audit.md).
