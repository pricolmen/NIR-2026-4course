# Адаптер моделирования: этап 10

[Simulation](../include/telemetry/simulation/simulation.hpp) соединяет неизменяемый [Scenario](scenario_format.md), физическую среду, Dispatcher, отдельные Detector и универсальный EventLoop. Реализация — [simulation.cpp](../src/simulation/simulation.cpp). Ядро получает только поступление задачи, результат, heartbeat, проверку срока и итоговый список доступности; сведений о физическом crash в его API нет. Движок исполняет нейтральные действия с ключами, без выбора детектора или стратегии распределения.

## Использование

```cpp
#include "telemetry/io/scenario_loader.hpp"
#include "telemetry/simulation/simulation.hpp"

const auto loaded = telemetry::io::load_scenario("examples/baseline/scenario.json");
telemetry::simulation::Simulation run{
    loaded.scenario, telemetry::simulation::Variant::fixed_rr};
const auto result = run.run();
run.validate_invariants();
const auto counts = run.dispatcher().task_store().counts();
```

Варианты: fixed_rr, fixed_ll, adaptive_rr, adaptive_ll. Один shared_ptr<const Scenario> можно передавать любому числу последовательных экземпляров. Каждая Simulation владеет своей очередью событий, детекторами, физическими узлами, историей попыток, нагрузкой и курсором RR. Сценарий и CSV не меняются. Чтение состояния — через константные ссылки clock(), dispatcher(), detectors(), physical(). Хранить Simulation нужно до завершения run(); копирование и перемещение запрещены.

run() вызывается один раз. Состояния: ready → running → completed либо failed. Успех означает исполнение всей очереди до включённого горизонта, с проверкой инвариантов; он допускает незавершённые задачи. Повторный/вложенный run() запрещён, в том числе после ошибки. Необязательный max_events — беззнаковый uint64-лимит действий движка; превышение бросает EventLimitExceeded и переводит запуск в failed. Ноль разрешает успех только при пустой очереди. Параллельное обращение к одному экземпляру не поддерживается.

## Восемь фаз одной отметки

| Фаза | Действие |
|---|---|
| 1 | Настоящие crash изменяют только физическую среду |
| 2 | Физическое завершение; немедленная проверка результата ядром; запуск следующей старой локальной попытки |
| 3 | Потенциальные отправки heartbeat, включая нулевую задержку |
| 4 | Приём heartbeat детектором; новые таймеры с новым поколением |
| 5 | Проверка сроков детектора; устаревшие поколения ничего не меняют |
| 6 | Один общий итоговый список ALIVE и набор новых FAILED; совместный отзыв логических назначений |
| 7 | Все поступления задач, по TaskId |
| 8 | Один dispatch после результатов, изменений доступности и поступлений; передача команд физической среде |

Фазы 6 и 8 создаются по запросу, только если есть соответствующая причина. Запросы той же отметки объединяются. Применение доступности само по себе не распределяет задачи. В фазе 6 ALIVE строится по состояниям детекторов; SUSPECT исключён без отзыва, FAILED окончателен и возвращает общий сортированный набор. Новые задачи фазы 7 добавляются после уже ожидающих и возвращённых задач. На фазе 8 Dispatcher последовательно учитывает новые назначения в нагрузке.

Heartbeat ровно на сроке проверки идёт раньше таймера. Допустимый результат на будущем FAILED принимается раньше исключения. Настоящий crash при завершении подавляет результат. Логический FAILED не отменяет старую физическую работу: её поздний результат проверяется по текущему назначению, номеру попытки и узлу. Распределение после настоящего crash и до его обнаружения допустимо; физическая среда сохраняет такую команду без запуска.

Ключи адаптера стабильны: поступление — TaskId; таймер — NodeId, вид SUSPECT/FAILED, поколение. Физические события используют ключи среды. Отметки и длительности сохраняют правила [time.md](time.md). События на горизонте, включая поступление и dispatch, исполняются; завершение после горизонта не создаётся.

## Наблюдение и ошибки

Необязательный SimulationAuditSink получает типизированное SimulationEvent вместе с EventKey текущего действия. Поток объединяет события ядра/среды, HeartbeatObserved, TimeoutObserved и DispatchBatch. Диагностика содержит решение детектора, до/после, актуальные пороги; heartbeat также содержит поколение и контакт. Несколько записей одного действия имеют одинаковый ключ, сохраняется последовательность синхронных вызовов. Ссылки действительны только на время callback; для хранения нужны копии.

Sink может читать состояние и проверять локальные инварианты. Во время callback допустимы промежуточные состояния между фазами и перед физической передачей всей пачки команд; межмодульная итоговая проверка выполняется после успешного завершения. Исключение sink или другого callback останавливает моделирование, передаётся вызывающему и сохраняет failed. Уже сделанные изменения и внешние записи не откатываются. Состояние после ошибки предназначено для диагностики, не для продолжения. При ошибке инициализации движок может остаться ready, при ошибке итоговой проверки — completed; успех всего запуска определяет Simulation::state().

Файловый журнал и метрики реализованы на [этапе 11](journal_metrics.md), команды CLI run/compare реализованы на [этапе 12](cli.md). simulation_available=true в --build-info обозначает доступность CLI моделирования. Типизированный поток сохраняется кодеком IO в версионированный JSONL.

## Сквозные проверки

[Integration tests](../tests/integration_tests.cpp) добавляют семь групп к предыдущим 50 тестам. Baseline проверяется во всех четырёх вариантах: RR назначения [1,2,1,2], завершения по ID [4,2,8,4]; LL назначения [1,2,2,1], завершения [4,2,6,6]. Crash-пример для fixed/adaptive RR даёт завершения [24,2,28,4], с отзывом и повторным назначением в 20. Blackout-пример во всех четырёх вариантах даёт SUSPECT в 15 и ALIVE в 25 без FAILED.

Дополнительно проверены ложный FAILED без физической отмены, старые результаты, совместные FAILED, пустой ALIVE и возврат, поступление на горизонте, результат/heartbeat ровно на сроке, crash при завершении, сообщение в полёте и пустой поток задач. Два скрытых физических состояния при одинаковых разрешённых наблюдениях дают одинаковые логические истории. Повтор и обратный порядок запуска вариантов сравниваются по тестовой сигнатуре событий/ключей/решений и итоговым историям; на этапе 11 дополнительно проверены полный канонический файловый журнал, метрики и отчёты. Эти маленькие проверки не являются исследовательским сравнением алгоритмов.

Результаты сборок и независимого аудита: [stage_10_audit.md](stage_10_audit.md).
